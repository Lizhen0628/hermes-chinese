# Bot 模式

**Bot 模式**把你的 [Hermes 配置档](./profiles.md) 变成一组具名 **Bot**。每个 Bot 都有自己的角色、模型、记忆、技能和头像；Bot 可以运行循环例程、在群聊中共同商议，并直接互相发消息。构建一个专属 Bot，一次即可永久拥有，一键即达。

Bot 模式**内置于 [桌面应用](./desktop.md)**且**默认开启** —— 无需安装。它会作为左侧边栏中 Sessions 旁的 **Bots** 标签页出现，当 Bots 标签页处于活动状态时，一个 **Routines** 磁贴会停靠在对话旁边。

:::tip 一个 Bot 就是一个配置档
无需学习新的基础概念：一个 Bot **就是** 一个 Hermes配置档 —— 隔离的配置、记忆、技能、凭据和聊天历史，全部位于 `~/.hermes/profiles/<name>/` 之下。Bot 模式是建立在该基础之上的一层 UI，因此你在其中所做的一切从 CLI 也可见：`hermes -p <bot> chat` 会打开同一个智能体，而 Bot 例程会出现在 `hermes cron list` 中。无需核心补丁，无需后台守护进程，无需额外存储。
:::

## Bots 窗格

花名册为每个智能体配置档显示一行：头像、最新消息预览和时间戳。

- **点击一个 Bot** 进入它的聊天 —— 每个 Bot 都有一个规范、持久的 **Bot 聊天**会话，它在 Bot 诞生的那一刻就被创建（并固定）。点击一行总是打开那个 Bot 聊天（即该行所预览的同一会话），即使你已经为这个 Bot 打开了其他标签页；那些标签页会保持在一旁。在标签栏中，Bot 聊天以该 Bot 的名字作为标题，因此两个打开的 Bot 一眼便能区分。
- **现在活跃** —— 花名册的活动筛选器包括焦点实时回合的所有者、过去 90 秒内写过内容的 Bot，以及近期有心跳工作进程的 Bot。仅有一个已连接的网关并不意味着某个 Bot 正在工作。
- **搜索**会随你输入过滤花名册。
- **隐藏一个 Bot** —— 右键点击一行 → **隐藏 Bot**，把你用不到的 Bot 从花名册和“现在活跃”条中移除。隐藏仅影响显示：@提及仍会解析，群聊成员关系不受影响，例程继续运行。一旦至少隐藏了一个 Bot，窗格标题中会出现一个**眼睛开关** —— 点击它可在原位置以变暗的方式显示隐藏的 Bot，然后右键 → **取消隐藏 Bot** 将其恢复。隐藏的 Bot 永不弹出提示，但会静默累积未读活动，眼睛图标会显示一个圆点，让你知道有事情发生。隐藏状态保存在该 Bot 的配置档元数据中，因此它会随该 Bot 出现在连接该后端的每个桌面上。

:::note 规范的 Bot 聊天是永久聊天
在一个 Bot 的规范聊天中输入 `/new`（或 `/reset`）会把这个关系分叉成一个临时会话 —— 而这正是 Bot 模式承诺永远不会发生的事。编辑器会改用它重定向到 `/compact`：全新的工作上下文，同一个对话。同一配置档上的常规会话保留完整的 `/new` 自由。
:::

### 将 Bot 组织到分区

分区是你自己创建的文件夹 —— **客户**、**团队**，或任何合适的分组 —— 作为自动按网关分组之外的第二条轴线。未创建任何分区时，花名册仍是它一直以来的普通列表。

- **创建一个分区**：从窗格的 **+** 菜单 → **新建分区**，或右键点击一个 Bot → **移动到分区** → **新建分区…**（在创建时即把该 Bot 归档进去）。
- **归档一个 Bot**：将它的行拖拽到一个分区上 —— 悬停时目标会高亮，按 **Esc** 取消拖拽 —— 或右键 → **移动到分区** 然后选一个。**从分区中移除**会把它放回 **未分配**。
- **重命名、重新排序或删除**分区：从分区标题的右键菜单（或悬停时出现的 **⋯**）操作；双击标题可重命名。标题可以像网关标题那样折叠。
- **删除分区永远不会删除 Bot** —— 它们会回到 **未分配**，并弹出提示提供 **撤销**。不要求确认。

成员关系保存在每个 Bot 的配置档元数据（`ui_meta`）中，因此一个 Bot 的分区会随它出现在连接该后端的每个桌面上。当花名册显示多个网关时，分区嵌套在每个网关的桶内。

## 创建 Bot

在名册中点击 **New Agent**。快速路径只需三个字段——**Name**、**Title**、**Description**——Bot 几秒内即可创建完成，并作为其新 Bot Chat 的第一条消息做自我介绍。

展开 **Advanced** 可显示完整的能力配置界面：

- **从现有配置档克隆** — 从另一个 Bot 的配置、技能、SOUL 和记忆出发，或选择 **Fresh profile** 从零开始。
- **创建空配置** — 完全跳过捆绑技能，构建一个最小化配置档。
- **模型与服务商固定** — 为 Bot 指定专属模型。Hermes 支持的任何服务商/模型组合都可以使用，不同的 Bot 可以并排运行在不同的模型上。不设置则继承启动配置档的模型。
- **自定义 SOUL.md** — Bot 的人设与常驻指令。
- **按技能、按工具集、按 MCP 服务器启用** — 精确勾选这位专家所需的能力。
- **共享密钥** — 默认情况下，新 Bot 与主配置档共享同一个 OAuth/token 池，因此凭证刷新不会互相失效。（旧版网关改为复制凭证——仍可工作，只是分叉了。）

### 选择它住在哪台机器上（"Create on"）

当 [Settings → Connections](./multi-connection-desktop.md) 中注册了多个连接时，New Agent 对话框会多出一个 **Create on** 选择器。选择一台设备，配置档就会被创建在**那台**机器的后端上——你的窗口不会切换网关。新 Bot 随后会以 Connections Bot 的形式出现在名册中（当名称在多台机器上存在时带有 `@name-device` 句柄），与它聊天会路由到它自己的机器。

只有单个连接时（常见情况），选择器隐藏，Bot 创建在你当前连接的机器上——完全保持旧行为。

远程创建注意事项：

- **克隆源**是*目标*机器的配置档（其 `default`）——远程机器没有你本地的配置档可供克隆。
- 实时 Capabilities 选项卡固定到目标机器的后端，因此创建过程中配置的技能、工具和 MCP 服务器会落到 Bot 将要居住的机器上。（旧版桌面构建对远程目标会回退到分阶段的 Skills/Tools/MCP 检查清单；两者都读取目标机器的目录。）
- 取消对话框会丢弃草稿配置档，无论它被创建在哪台机器上。

**Edit Profile**（右键点击 Bot）可随时在实时配置档上重新打开同一界面：头像、标题、描述、模型固定、技能、工具集、MCP 服务器以及完整的 SOUL.md。

**Duplicate**（右键点击）可完整克隆一个 Bot——配置、技能、SOUL.md、记忆及其外观。**Delete Profile** 会永久删除一个 Bot，使用与桌面配置档菜单相同的破坏性确认对话框；默认配置档无法删除。

## 头像

每个 Bot 都有一张脸：

- **团子脸**（默认）——根据 Bot 名称确定性地绘制出的软体脸：同名同脸，永远不变。当你在 New Agent 中输入名称时，脸会实时跟随；点击 **Randomize** 重新随机，点击 **Lock face** 即可在名称改变后仍保留下你喜欢的那张脸，或从六种轮廓（圆形、有机、方盒、凸块、云朵、太阳）中固定一种，其余仍从名称推导。
- **几何脸** — 经典的 7 种形状 × 10 种颜色。在一轮聚焦的实时对话期间，所属 Bot 会倾斜并向上看，伴随三个动画圆点，回合结束后逐渐回到空闲状态。归属包括连接，因此不同网关上的同名 Bot 不会借用彼此的姿势。后台工作者保留其现有的工作动画；照片、团子脸和徽记保留各自的渲染方式。
- **上传的图片** — 你喜欢的任何图片。
- **AI 生成的肖像** — 配置了图像后端后，可就地生成（走标准 `image.generate` RPC，本地与远程网关均可用）。
- **像素宠物** — 来自 [petdex gallery](./features/pets.md) 的伙伴，在 Bot 繁忙时在头像旁弹跳。在终端运行 `hermes pets` 可浏览图库。

Bot 的外观、标题和描述存储在后端的配置档元数据中，因此同一个 Bot 在所有连接到该后端的桌面上呈现方式都相同。

## Routines

**Routines** 面板把周期性任务绑定到负责执行它们的 Bot 上 —— 「每天早上帮我总结收件箱」就放在负责它的 Bot 旁边。该面板仅在 Bots 标签页处于活动状态时停靠在聊天旁边，切回 Sessions 时会自动让位（较旧的桌面版会始终显示）。结构化的调度选择器用于构建调度（先选频率，再填写真正需要的细节），另外还有一个 Advanced 字段可直接编写原始的 Hermes 调度字符串。

Routines 就是普通的 [Hermes 定时任务](./features/cron.md)，命名空间格式为 `[bot:<name>] <routine>` —— 它们也会出现在 `hermes cron list` 和核心 Cron 页面中。运行结果会落在 Bot 自己的聊天历史中，因此结果就出现在你本来就会与该 Bot 对话的地方。

## 群组与群聊

在某个成员回合期间发送的消息会排队等待该房间当前的驱动完成，包括同一线程中的回复。它们不会打断该成员，也不会把未读消息标记为已读。Stop 会取消排队的后续继续操作，并搁置成员直到恢复。前台等待结束后，安静的房间还会继续观察超时成员 21 分钟；该观察窗口不会延长回合本身。未解决的成员故障在房间稳定后仍会显示在折叠的 Activity 摘要中。展开 Activity 可查看回合序列；重新 @ 该成员即可再试一次。含糊不清的提交失败不会被自动重新提交。


右键点击本地 Bot → **Manage groups**，即可将其加入或移出任意数量的群聊。可以独立选择已有群组，也可以内联创建一个。本地成员关系存储在 Bot 的、与后端同步的配置档元数据中，因此会跟随该配置档跨桌面端保持一致；带有单个旧版群组的较旧配置档仍可继续使用。Connections Bot 通过 New Group Chat 选择器加入，并在房间的共享状态中保持带有来源标识。

**房间跟随你的网关，而不是某台 Desktop。** 每个房间的近期对话记录、成员、图片和名称都会镜像到你的 Desktop 所连接的**每个**网关的共享配置档元数据中，并按网关分别进行版本管理，因此两个 Desktop 同时写入时会合并而不是相互覆盖。在另一台机器上使用同一个网关（局域网、Tailscale，任何地方）打开 Hermes Desktop，该房间就会连历史一起出现；仅连接网关的客户端也能看到它。房间拥有持久的内部身份，因此重命名只会改变各处的显示名称，解散会在所有客户端上永久删除（包括当时处于离线的客户端），而重新创建同名群组则会开启一个真正全新的房间。如果某个网关宕机或被移除，不会丢失任何东西：每个已连接的 Desktop 都在本地保留完整房间，并在重新连接到任何网关时把数据重新灌入。(完整的编排日志保存在每个 Desktop 的本地存储中；共享镜像只是有界的近期历史投影。)

群组与 Bot 私聊一样，是同一条按活动排序的名单中的独立行。一个 Bot 即使属于多个群组也只保留一行私聊，而每个群组都有自己的房间行，带有成员数量、最新消息预览、时间戳和 needs-you 状态。

使用房间旁的 **Move up** 和 **Move down** 箭头来选择它在各房间中的位置。在第一次移动之前，现有的置顶优先、按近期活动排序保持不变。移动之后，房间顺序会保存在此 Desktop 上并在重新加载后依然保留；新房间会在其置顶或非置顶区间内跟随显式排序的房间之后。移动不能跨越置顶边界，过滤也不会从保存的顺序中丢弃被隐藏的房间。这些控件只会重排实际的 Group Chat 房间，不会重排用户创建的 Bot 文件夹，也不会改变成员关系或网关归属。

在任何群组行（2–6 个 Bots）上点击 **Open chat** 会打开一个共享房间，让整个群组在其中协同：

- **一个可见的对话。** 公开消息和每位成员的回复都按到达顺序保持可读，附有发言者姓名和时间戳。开启另一个话题不会折叠较早的回复。**Reply in thread** 会在不重排房间的情况下继续该话题；**Activity** 是次要的状态视图，而不是消息的替代品。私密的 Bot Chat 仍然彼此独立。
- 你的消息最多触发**三轮串行的**成员回合。被 @ 提及的 Bots 会回应（没人被提及时所有人都可回应）；每个 Bot 要么简短回复，要么跳过，当整整一轮都保持沉默时房间即告稳定。
- 队友可以用 `@hermes` 交接给主导 Bot，在较旧的已保存房间中也适用；位于其他网关上的 Bots 保留其带设备限定的标签（例如 `@default-vera`）。
- Bots 之间用 `@name` 相互拉入，并把真正需要判断的问题用 `@user` 上报给你 —— 此时群组行会显示 **needs you** 徽标。待答问题和命令审批也会点亮该徽标；解决最后一个提示只会清除提示关注，而不会清除独立的人为提及。提示会跟随重命名后的房间，而解散则会使其作废，即使某位成员的进行中轮询稍后才到达。
- 硬性上限（每次发送 10 条消息、3 轮）防止房间空转。
- 每位成员都保有自己的持久 `Group: <name>` 会话，因此房间上下文会像其他任何会话一样得以保留。
- **并非每个 Bot 都会回复每条消息。** 发言是每位成员自己的选择 —— 一个 Bot 只有在有新的内容可补充时才回复，否则跳过；@ 提及特定成员会把该轮范围限定到他们身上。预期你会看到你 @ 的人（或任何有话要说的人）发言，其他人保持安静。
- **当你关闭 Desktop 时房间仍在运行。** 当某个房间的所有成员都位于同一个网关上时，该网关通过一个持久驱动来负责回合调度：关闭 Hermes Desktop（或断开其连接）不会让讨论中的房间中断，Desktop 只是在重连时从房间日志追赶进度。网关上的 `groups.capabilities` 在适用时会报告 `driver: true`。成员分散在多台机器上的房间则不同：每位成员的回合都在其自己的网关上运行，而 *Bot 到 Bot 的消息传递* 中描述的跨连接信使仍然适用于它们。
- **房间可以跨机器。** New Group Chat 选择器可以从任意已注册连接中安排 Bots；每位成员的回合都在其自己的机器上、在当地的`Group: <name>` 会话中运行。跨机器成员在房间中以及其他成员的对话记录中带有设备徽标（`dixie · Mac Mini`），而消歧后的 `@name-device` 句柄可用于房间提及 —— 因此两台机器上的同名 agents 永远不会混淆。
- **插件可以观察成员的工作。** 持久房间日志记录 `turn.started` 和 `turn.settled`；成员在这之间所做的（工具、审批、流式文本）会通过 [`on_room_member_activity`](/user-guide/features/hooks#on_room_member_activity) 钩子投射给插件，带有房间、成员和回合坐标，因此社区客户端可以在 Group Chat 之上构建工具卡片和实时成员状态，而无需阅读 Hermes 内部实现。

## 机器人之间的消息传递

机器人之间会带出处说明地互相发消息，而且你可以从任何聊天里把工作交接出去：

- **@提及** — 在任何聊天中输入 `@researcher have a look at this`，输入框的 `@` 自动补全会帮你选对机器人；发送时，提及会对着实时名册解析，活动中的机器人会确切知道你指的是谁（配置档、友好名称，以及跨连接机器人的设备）。机器人随后会自己组织消息并用 `message_agent` 发送——你的文字不会被逐字转发，回复会以该智能体的名义注明来源。电子邮件地址或未知的 `@` 会原样放行。在其他已连接机器上的机器人也可以用同样方式联系：Desktop 会通过那条连接自己的 socket 转发消息（见下方 *跨机器的机器人*）。
- **重命名后的机器人会保持标签同步** — 给机器人一个友好名称（在其聊天标题栏点铅笔图标，或运行 `hermes profile rename`），它就能用该名称被提及：标题为 *Research Buddy* 的机器人会响应 `@research-buddy`（以及 `@researchbuddy`），在普通聊天和群组房间里都一样。输入框的 `@` 自动补全会提供重命名后的标签，在你输入旧配置档名称时也会匹配，旧名称同样一直可以解析。
- **私信** — 每个机器人聊天都带有 `message_agent` 工具：机器人通过调用 `message_agent(target="researcher", message="…")` 给队友发消息。该工具会对着实时名册校验目标，自动给发送者的消息加上 `Message from 🤖 <sender> (@<sender>):` 的出处前缀，并投递到队友的规范机器人聊天中。投递是**发后不管（fire-and-forget）**的：发送者会收到确认，结束自己的回合，回复稍后作为后台完成通知到达。消息以真实参数形式传输（不经过任何 shell 解释——引号、`$(...)` 和反引号都原样送达），而且机器人自己组织消息，不会转发你的原话。队友名册——包含各配置档标题/描述中的**名字和角色**——是每个机器人聊天系统提示词的一部分，因此机器人在选择收件人之前就知道谁负责什么。该工具**仅**存在于由机器人模式管理的安装中的规范机器人聊天会话里；普通聊天、群组房间成员会话和 CLI 会话永远看不到它。

本地消息也能到达在 Desktop 或 TUI 中保持打开的机器人聊天。接收端后端保有所有权：它通过现有的通知轮询器读取持久化入口消息，在空闲时立即接纳，或等待正在运行的回合和已排队的人工提示完成。`queued` 确认表示已经持久化接纳，**不是**回复已经完成。目标配置档把投递 ID 和回执保留在 `runtime/bot_live_delivery/` 下；`settled` 才是完成确认。崩溃或被取消的导入回合不会自动重放，固定到已离开所有者的待处理工作仍可查看，而不会被静默重跑。不要重发结果未知的投递。不具备实时投递能力的老后端会沿用现有的所有权拒绝逻辑；升级后请重启该后端。

后端会在构建提示词时自动把消息传递协议教给每个机器人的规范机器人聊天会话——包括队友从 CLI 无头打开它的时候。只有规范机器人聊天会得到协议部分；你的普通会话和你的 SOUL.md 保持不受影响。这由 `config.yaml` 中的 `agent.bot_mode_protocol` 控制（默认：开启）：

```yaml
agent:
  bot_mode_protocol: true   # inject the bot-to-bot messaging protocol into canonical Bot Chats
```

:::note
机器人之间的投递是按次调用进行的：接收方机器人在下次运行时才会取走消息。在对话中途实时打断机器人的能力是未来的工作。
:::

### 失败的回合会安全重试

本地一次性投递把活动会话拒绝码与其人类可读消息分开保存。`SESSION_NOT_OWNED` 会产生 `target_busy`；不可读的协调注册表不会被误标为其他所有者。没有该代码标记的老本地 CLI 仍使用历史上的拒绝措辞。

投递失败的回合最多重试一次，并且只有在重试确实有帮助时才会重试。瞬时失败（目标运行时离线、投递超时、服务商限流或服务器错误）会原样重跑同一个机器人聊天会话。上下文溢出的失败也会重跑同一会话——重试的回合会在调用模型之前，通过标准上下文压缩流程对超阈值记录进行压缩，因此重试能在原始尝试放不下的地方放得下。鉴权、配额和配置失败永不自动重试：第二次尝试无法解决它们，只会消耗配额，因此失败会立即暴露。重试回合永远不会开启新会话——你的机器人聊天历史和上下文保持完好。

当目标没有在线的 Desktop 或 TUI 所有者时，本地投递会通过一次安静的 CLI 回合打开该配置档的规范机器人聊天。传输层会优先选用发送方运行时 Python 解释器旁边的 Hermes 入口点，因此当那个同级入口点存在时，服务 `PATH` 上无关或较老的 `hermes` 无法抢先执行。`--in ~` 选择工作目录；显式的机器人聊天标题会在目标配置档的会话数据库中解析。

### 投递失败时：带类型的失败原因

失败的 bot 回合或中继投递，在人类可读的错误文本之外，端到端地携带一个机器可读的 `reason` 代码：目标网关对失败进行分类（`provider_auth_or_access`、`provider_quota_limit`、`provider_rate_limit`、`provider_server_error`、`context_overflow`、`missing_config`、`model_unavailable`、`runtime_offline`、`queued_expired`、`delivery_timeout`、`target_busy`、`unknown`），Hermes Desktop 将其转发，发送方智能体的完成通知会在错误文本之前打上 `[reason: <code>]` 标记。调用方智能体可以基于该代码进行分支判断——"重新登录"还是"稍后重试"——而无需解析服务商的文案。Hermes Desktop 的需关注徽标也使用相同的代码。

### 跨已连接机器收发消息（Desktop 中继）

你在 **Settings → Connections** 中注册的每一条网关——本地、远程 URL、SSH、Hermes Cloud、Docker——都是 Hermes Desktop 保持打开的一条持久连接，Bot Mode 会自动使用这些连接来收发消息。无需额外设置：

- **名单会自动传播。**Hermes Desktop 运行期间，会定期告知每个已连接的网关：*其他*连接上都有哪些智能体。于是每个 Bot Chat 的队友名单都会列出它们（"Teammates on OTHER connected machines"），包含名称、角色以及所在机器——名单会在智能体出现、消失或改名时刷新（能力纪元）。
- **`message_agent` 可以直接联系它们。**你笔记本电脑上的 Bot 用 `message_agent(target="moxie", …)` 给云端智能体发消息，就像给本地队友发消息一样。如果多个机器上存在相同的句柄，用 `target="moxie@<connection>"` 消歧（工具的报错会告诉 Bot 具体的格式）。投递经由 Hermes Desktop：发送方网关将消息排队，Hermes Desktop 中继到目标连接自己的网关上，目标 Bot 在其规范 Bot Chat 中运行一个回合，回复作为本地私信所用的同一个后台完成通知返回给发送方。
- **Hermes Desktop 是信使。**跨连接投递在知晓两个连接的 Hermes Desktop 运行期间可用（它持有套接字和凭据——网关彼此看不到对方的认证信息）。如果投递中途关闭了 Hermes Desktop，发送方的 Bot 会被告知回复未到达，而不是一直挂起。若要在不经过 Hermes Desktop 的情况下实现常开的机器间消息传递，可注册一个对等端（`hermes peer`，见下文）——两条路径可以共存。

### Bot 发起的跨机器私信（`hermes peer`）

一台机器上的 Bot 可以给**另一台机器的网关**上的 Bot 发消息，无需任何 desktop 参与。将对方网关注册为*对等端*（其 API 服务器 URL + `API_SERVER_KEY`）：

```bash
hermes peer add spark --url http://spark.lan:8377 --key <API_SERVER_KEY>
hermes peer list
hermes peer dm spark < /tmp/dm.txt        # 消息体来自文件（不被 shell 解释）
hermes peer dm spark/researcher < /tmp/dm.txt   # 多路复用对等端上的具名配置档
hermes peer run spark --idempotency-key ticket-123 < /tmp/long-task.txt
hermes peer status spark run_abc123
hermes peer stop spark run_abc123
```

`hermes peer dm` 经由对等端现有的 API 服务器投递到远程智能体的规范 Bot Chat，在那里运行一个智能体回合，并将回复打印到 stdout——正是本地 `hermes -p <bot> chat` 命令的跨机器孪生版本。

仅在短查询和回执场景使用 `peer dm`，因为它会一直占用一个 HTTP
连接直到该回合结束。对于耗时的回合，`peer run` 会立即返回
`run_id`；用 `peer status` 轮询它。该运行继承规范 Bot Chat 的对话记录，
一个稳定的 `--idempotency-key` 能让重试返回原始运行，而不是启动重复工作。
使用 `peer stop` 并给出那个确切的 run ID 来中断它，而不会误指向其他回合。

一旦注册了对等端，教给每个 Bot Chat 的消息协议（`agent.bot_mode_protocol`）会自动包含对等端名单，而 `message_agent` 直接接受对等端目标——`message_agent(target="spark/researcher", …)`，或者 `target="spark"` 表示对等端的主智能体——因此**你的 bot 会自行了解到**其他机器上存在队友以及如何联系它们。注册或移除对等端会在下一次消息时刷新每个 Bot Chat 的协议（能力纪元）。

要求：对等端机器运行 `api_server` 网关平台并配置一个强 `API_SERVER_KEY`；可达性是你自己网络的事（LAN、Tailscale、VPN）。该密钥是凭据，存放在 `~/.hermes/.env` 中的 `HERMES_PEER_<NAME>_KEY`；对等端名称/URL 存放在 `config.yaml` 的 `bot_peers` 下。

:::note 单向可达性（NAT）
跨网关链接是直接的网关到网关连接——Hermes Desktop 是查看器，不是中继。
位于家庭 NAT 之后的网关可以主动拨号到公网对等端（笔记本 → VPS 可行），
但反方向没有入站路由（VPS → 家庭 失败），除非你的网络提供了这样的路由。
如果你的 Group Chat 跨越 NAT 边界，将房间的权威放在所有参与者都能
访问的主机上（通常是公网 VPS），或者用 Tailscale/VPN 桥接网络。
:::

### 转移托管房间权限

权限接管是一项**运维恢复程序**，而不是原子的移交操作。
请在相应的网关上使用现有的 JSON-RPC 方法 `groups.promote` 和 `groups.demote`。
不存在 `groups.peer.promote` 或 `groups.peer.demote` 方法；`groups.capabilities` 会列出你的网关所支持的方法。

:::warning 在提升前围栏旧写入方
在发送 `confirm: true` 之前，请先确认先前的权限持有者**无法提交**，并将该围栏保持到位，直到其被降级。停止其房间写入进程并阻止自动重启，或采用同等的基础设施围栏手段。网络超时、断开 Desktop，或 `groups.stop` 都不能作为证据：旧网关可能仍在运行，停止一个回合并不会撤销房间权限。如果你无法建立围栏，请不要提升。
:::

1. **检查副本覆盖情况。** 在替换网关上，通过 `{"room_id":"ROOM_ID"}` 检查
   `groups.replica_state`，并将 `last_seq` 与 `latest_seq` 进行比较。计划内接管要求达到完整副本；
   提升操作本身不会检查这一覆盖情况。`groups.replicate` 在摄取完
   `groups.log` 返回的分页后会报告 `caught_up`；仅凭对端注册并不能证明替换方
   已拥有房间历史。追平状态描述的是最后复制的分页，并非证明旧写入方已停止
   或不存在更新的事件。对于计划内迁移，先静默写入方，复制到最终游标，然后维持围栏。
   对于灾难恢复，需考虑从未到达副本的任何历史记录。
2. **仅在旧写入方被围栏时进行提升。** 在替换方上：

   ```json
   {"jsonrpc":"2.0","id":1,"method":"groups.promote","params":{"room_id":"ROOM_ID","confirm":true,"reason":"planned-handover"}}
   ```

   `room_id` 和 `confirm: true` 为必需项；`reason` 为可选项，默认值为
   `authority-unreachable`。确认是你断言先前权限持有者无法提交，**并非**
   请求自动对其围栏。若没有确认，调用会返回错误 `4118`。成功的结果会报告
   `authority_gateway_id` 和 `authority_epoch`（复制后的 epoch 加一）。
3. **在旧权限持有者恢复服务前先降级它。** 在对旧网关施加此 RPC 时，
   通过一个受控的恢复连接，保持其正常的房间写入方处于围栏状态。将示例中的网关 ID 和 epoch
   替换为成功提升所返回的确切值：

   ```json
   {"jsonrpc":"2.0","id":2,"method":"groups.demote","params":{"room_id":"ROOM_ID","observed_gateway_id":"NEW_GATEWAY_ID","observed_epoch":2}}
   ```

   三个参数均为必需项。不要猜测未来的 epoch：降级需要的
   是较新权限持有者的证据，而非凭空捏造的值。它会记录
   `authority.lost` 并采用所观测到的谱系；重复相同的谱系
   是幂等的。如果旧主机不可用，将其保持围栏，并在恢复其正常写入方之前执行此步骤。
4. **验证并重新连接。** 读取两个网关上的 `groups.state`，并将
   `room.authority_gateway_id` 和 `room.authority_epoch` 与提升
   结果进行比较。旧权限持有者的发送必须被拒绝；引导客户端指向替换方。
   降级会对写入施加围栏；它不会合并历史，也不会自动将
   旧的权威存储转变为同步副本。

在旧网关仍可写入的情况下进行提升，会让两个独立的
`state.db` 存储同时接受消息并产生分歧的历史。替换方拥有更高的
epoch 并不会远程禁用旧写入方；分裂脑并不要求 epoch 相等。
如果历史已经分歧，请围栏写入方并保留两份历史以供恢复，
而不是假设提升、降级或重放会将它们合并。

## 跨机器的 Bots

当你在 **设置 → 连接** 中注册多个后端——本地运行时、远程网关、SSH 主机、Hermes Cloud 实例——花名册会持续显示来自**每一个**已连接来源的 Bots：SSH 来源会在不在远程机器上启动任何东西的情况下进行清点，而暂时无法访问的机器会保留其最后已知的行，而非消失。当同一个配置档名称存在于多个来源时，句柄会通过 `@name-device` 进行消歧（例如 `@research-homelab`）。一个 Bot 的聊天、会话、记忆和例程都存在于拥有该配置档的机器上。

点击一个“连接”中的 Bot 并**不会**将你的窗口切换到那台机器上——请留在你的聊天中并 `@mention` 它、将其安排在群聊中，或直接使用 **创建于** 选择器在其上创建新的智能体。云端和本地智能体通过这种方式共享一个花名册：注册你的 Hermes Cloud 实例和你的桌面端（例如，通过 Tailscale 或 SSH），它们的 Bots 就能互相发消息并坐在同一个房间里，而每个智能体的工作都在其自己的机器上运行。跨越这些机器的 Bot 对 Bot 私信会自动经过 Desktop 中继（参见上文*跨已连接机器收发消息*）。

有关完整的多连接指南，请参见 [将 Desktop 连接到多个 Hermes 实例](./multi-connection-desktop.md)。

## 热 Bot 后端（同时运行多少个 bot）

每个本地 Bot 都在自己的后端进程中运行，而 Desktop 最多保持 **设置 → 高级 → 热 Bot 后端** 所设定的数量（默认 3，每个约 60 MB）处于存活状态。空闲的后端会在该设置旁的空闲超时（默认 10 分钟）后被回收；`desktop.log` 中紧随空闲回收消息之后的 `Hermes backend for profile "<name>" exited (1)` 行就是那次清理，而非崩溃。当所有槽位都繁忙时你打开的 Bot 会等待最多 30 秒以获取槽位，随后失败并提示*等待空闲本地槽位超时*。

读取另一个 Bot 的聊天历史和后台转录刷新**不会**占用槽位——只有交互式打开或正在运行的回合才会。如果你驱动一个大型阵容（成员很多的群聊，或跨越多个配置档的看板派发），请将“热 Bot 后端”提升至你预计同时处于活动状态的 Bots 数量，并为机器配备与之匹配的内存。将其设置得高于你实际使用的配置档只会增加启动工作量。

## 将其关闭

Bot Mode 是一个捆绑的桌面插件。在 **能力 → 插件 → Bots** 中将其 **Desktop** 开关关闭——花名册、例程面板和撰写器中间件会实时注销，无需重启。你的配置档、会话和定时任务无论哪种情况下都不受影响；Bot Mode 从不拥有你的数据，它只负责渲染数据。

还有一个偏好设置可将规范 Bot 聊天从常规侧边栏会话列表中隐藏，使它们仅出现在 Bots 面板内。（这使用核心的隐藏会话标志；在较旧的网关上，这些聊天只会保持可见。）

## CLI 对等性

因为 Bots 就是配置档，一切都存在终端等价操作：

| 在 Bot Mode 中 | 在 shell 中 |
| --- | --- |
| 与一个 Bot 聊天 | `hermes -p <bot> chat` |
| 一个 Bot 的文件、技能、记忆 | `~/.hermes/profiles/<bot>/` |
| 例程 | `hermes cron list`（作业名为 `[bot:<name>] …`） |
| 创建 / 检查配置档 | `hermes profile create`、`hermes profile list` |

参见 [配置档](./profiles.md) 了解底层原语，并参见 [配置档命令](../reference/profile-commands.md) 了解完整的 CLI 参考。
