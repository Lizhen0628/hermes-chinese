# Bot Mode

**Bot Mode** 将你的 [Hermes 配置档](./profiles.md)打造成一批具名的 **Bot**。每个 Bot 都有自己的角色、模型、记忆、技能与头像；Bot 执行周期性例行任务、在群聊中共同商议，并直接互相发送消息。只需构建一次专职 Bot，它便永久存在，随时一键可用。

Bot Mode **内置于[桌面应用](./desktop.md)**中，并**默认开启**——无需安装。它会以 **Bots** 标签页的形式出现在左侧边栏的 Sessions 旁边，当 Bots 标签页处于活动状态时，**Routines** 磁贴会停靠在对话旁。

:::tip Bot 就是一个配置档
没有新概念需要学习：一个 Bot **就是**一个 Hermes 配置档——在 `~/.hermes/profiles/<name>/` 下拥有隔离的配置、记忆、技能、凭据与聊天历史。Bot Mode 只是这一原语之上的 UI，因此你在其中所做的一切在 CLI 中同样可见：`hermes -p <bot> chat` 会打开同一个智能体，而 Bot 的例行任务也会出现在 `hermes cron list` 中。无需核心补丁，无需后台守护进程，无需额外存储。
:::

## Bots 面板

名册为每个智能体配置档显示一行：头像、最新消息预览与时间戳。

- **点击某个 Bot** 即可进入其聊天——每个 Bot 都拥有一个规范的、持久的 **Bot Chat** 会话，在 Bot 诞生那一刻即被创建（并固定）。点击某一行总是打开该 Bot Chat（与行预览相同的会话），即便你为这个 Bot 打开了其他标签页；那些标签页会保持打开并排显示在旁边。在标签条中，Bot Chat 以 Bot 的名字作为标题，因此两个打开的 Bot 一眼即可区分。
- **Active now**——名册的活动筛选器包括聚焦的实时轮次的所有者、最近 90 秒内有过写入的 Bot，以及近期有心跳的 worker 的 Bot。仅有一个已连接的网关并不意味着该 Bot 正在工作。
- **搜索**会随你输入实时筛选名册。
- **隐藏 Bot**——右键点击某行 → **Hide Bot**，即可将你不用的 Bot 从名册和 Active-now 区域中移出。隐藏仅作用于显示：@提及依然能解析，群聊成员关系不受影响，例行任务继续运行。一旦至少有一个 Bot 被隐藏，面板标题处会出现一个 **眼睛切换按钮**——点击它即可在原位以灰暗样式显示被隐藏的 Bot，然后右键 → **Unhide Bot** 将其恢复。被隐藏的 Bot 永远不弹提示，但会静默累积未读活动，眼睛图标会显示一个圆点，让你知道有事情发生了。隐藏状态保存在 Bot 的配置档元数据中，因此它会在连接到该后端的所有桌面上跟随该 Bot。

:::note 规范的 Bot Chat 是一个永久聊天
在某个 Bot 的规范聊天中输入 `/new`（或 `/reset`）会把这段关系分叉到一个临时会话中——这正是 Bot Mode 承诺永不发生的事。输入框会将其改为 `/compact`：全新工作上下文，同一段对话。同一配置档上的常规会话则保留完整的 `/new` 自由。
:::

### 将 Bot 组织到分组中

分组是你自己创建的文件夹——**Clients**、**Team**，任你合适的名称——作为自动按网关分组的另一条坐标轴。没有创建任何分组时，名册就是它一直以来那样的一份普通列表。

- **创建一个**：从面板的 **+** 菜单 → **New section**，或右键点击某个 Bot → **Move to section** → **New section…**（在您创建它的同时将该 Bot 归档进去）。
- **归档一个 Bot**：将其行拖到某个分组上——悬停时目标会高亮，按 **Esc** 取消拖拽——或右键 → **Move to section** 然后选一个。**Remove from section** 会将其放回 **Unassigned**。
- **重命名、重排序或删除**分组：从其标题的右键菜单（或悬停时出现的 **⋯**）操作；双击标题可重命名。标题的折叠行为与网关标题相同。
- **删除分组绝不会删除 Bot**——它们会回到 **Unassigned**，并提供一个 **Undo** 提示。不会要求确认。

成员关系存储在各自 Bot 的配置档元数据（`ui_meta`）中，因此一个 Bot 所属的分组会在连接到该后端的所有桌面上跟随它。当名册显示多个网关时，分组会嵌套在各网关的桶内。

## 创建 Bot

在花名册中点击 **New Agent**。快捷路径只需三个字段 —— **Name**、**Title**、**Description** —— Bot 几秒内即可诞生，并以它新 Bot Chat 的第一条消息进行自我介绍。

展开 **Advanced** 折叠区域可进入完整的能力界面：

- **从现有配置档克隆** —— 以另一个 Bot 的配置、技能、SOUL 和记忆为起点，或选择 **Fresh profile** 从干净状态开始。
- **创建空配置** —— 完全跳过捆绑技能，得到一个最小化配置档。
- **固定模型与服务商** —— 为 Bot 指定专属模型。Hermes 所知的任意服务商/模型组合均可使用，不同的 Bot 可以并行运行在不同的模型上。不设置则继承启动配置档。
- **自定义 SOUL.md** —— Bot 的人格与常驻指令。
- **按技能、按工具集、按 MCP 服务器启用** —— 精确勾选这位专家所需的能力。
- **共享密钥** —— 默认情况下，新 Bot 与主配置档共用同一 OAuth/token 池，因此凭据刷新不会相互失效。（旧版网关则改为复制凭据 —— 仍可用，只是分叉了。）

### 选择它驻留在哪台机器上（"Create on"）

当 [Settings → Connections](./multi-connection-desktop.md) 中注册了多个连接后，New Agent 对话框会多出一个 **Create on** 选择器。选定某个设备后，配置档就创建在**那台**机器的后端上 —— 你的窗口无需切换网关。新 Bot 随后会以 Connections Bot 的形式出现在花名册中（当名称在多台机器上存在时，带有 `@name-device` 句柄），与它聊天会路由到它自己所在的机器。

只有一个连接时（常见情形），该选择器会被隐藏，Bot 创建在你当前连接的机器上 —— 完全等同于旧行为。

远程创建的注意事项：

- **克隆源**是*目标*机器的某个配置档（其 `default`）—— 远程设备没有你的本地配置档可供克隆。
- 实时 Capabilities 选项卡会固定到目标机器的后端，因此创建过程中配置的技能、工具和 MCP 服务器都落在 Bot 将要驻留的那台机器上。（旧版桌面构建对远程目标会退回到分阶段的 Skills/Tools/MCP 清单；两者读取的都是目标机器的目录。）
- 取消对话框会丢弃在相应机器上创建的草稿配置档。

**Edit Profile**（右键点击某个 Bot）可随时在实时配置档上重新打开同一界面：头像、标题、描述、模型固定、技能、工具集、MCP 服务器以及完整的 SOUL.md。

**Duplicate**（右键）会完整克隆一个 Bot —— 配置、技能、SOUL.md、记忆以及外观。**Delete Profile** 会永久删除一个配置档，并带有与桌面配置档菜单相同的破坏性确认；默认配置档无法删除。

## 头像

每个 Bot 都有一张面孔：

- **团块面孔**（默认）—— 由 Bot 名称确定性生成的软体面孔：名称相同，面孔永远相同。在 New Agent 中输入名称时，面孔会实时跟随；点击 **Randomize** 可重新掷取，点击 **Lock face** 可锁定你喜欢的那张、即便名称改变也不受影响，也可钉选六种轮廓之一（round、organic、boxy、nub、cloud、sun），而其余一切仍由名称决定。
- **几何面孔** —— 经典的 7 种形状 × 10 种颜色。在一个聚焦的实时回合中，所属 Bot 会倾斜并向上看，并配以三个动画圆点，回合结束后再缓缓回到闲置状态。所属关系包含连接，因此不同网关上同名的 Bot 不会借用该姿态。后台工作进程保留其原有的工作动画；照片、团块面孔和印记则保留各自的渲染方式。
- **上传的图片** —— 任意你喜欢的图片。
- **AI 生成的肖像** —— 在配置了图像后端时就地生成（走标准的 `image.generate` RPC，在本地和远程网关上均可工作）。
- **像素宠物** —— 来自 [petdex gallery](./features/pets.md) 的伙伴，在 Bot 忙碌时于头像旁蹦跳。在终端运行 `hermes pets` 即可浏览该图库。

Bot 的造型、标题和描述都存在后端配置档的元数据中，因此同一个 Bot 在每一个连接到该后端的桌面上都呈现相同的样貌。

## 例行任务

**Routines** 面板把周期性任务挂到执行它的 Bot 上——"每天早上汇总我的收件箱"就放在负责它的 Bot 旁边。该面板仅在 Bots 标签页处于活动状态时停靠在聊天旁边，切回 Sessions 时就会让位（较老的桌面版会始终保持其可见）。结构化的计划选择器用于构建计划（先选频率，再只显示真正相关的细节），并提供一个高级字段用于直接暴露 Hermes 的原始计划字符串。

Routines 就是普通的 [Hermes 定时任务](./features/cron.md)，命名空间格式为 `[bot:<name>] <routine>`——它们同样会出现在 `hermes cron list` 和核心 Cron 页面中。运行结果会落到 Bot 自己的聊天历史里，所以结果就出现在你平时与那个 Bot 对话的位置。

## 群组与群聊

成员轮次期间发送的消息会排在当前房间的活动流之后，包括同一线程中的回复。它们不会打断该成员，也不会把未读消息标记为已读。Stop 会取消排队的后续消息，并在恢复前暂停所有成员。安静的房间在前台等待结束后，还会对超时的成员再观察 21 分钟；这一观察窗口不会延长该轮次本身。房间稳定后，未解决的成员故障仍会在折叠的 Activity 摘要中可见。展开 Activity 可查看轮次序列；重新 @ 该成员以重试。无法确定的提交失败不会被自动重新提交。


右键点击本地 Bot → **Manage groups**，即可将其添加到任意数量的群聊或从中移除。可以分别选择已有的群组，也可以就地新建。本地成员关系存储在 Bot 的后端同步的配置档元数据中，因此该成员关系会随该配置档跨桌面端保持——带有单个旧式群组的老配置档仍可继续使用。通过 New Group Chat 选择器加入的 Connections Bot 会保持来源限定地出现在房间的共享状态中。

**房间跟随你的网关，而不是某一台 Desktop。**每个房间的近期记录、成员、头像和名称都会镜像到你的 Desktop 所连接的**每一个**网关的共享配置档元数据中，并按网关分别版本化，这样两台 Desktop 同时写入时会合并而不是互相覆盖。在同一网关（局域网、Tailscale，任何地方）上用另一台机器打开 Hermes Desktop，该房间及其历史就会出现；仅连接网关的客户端也能看到它。房间带有持久化的内部身份标识，因此重命名只会改变其在所有地方的显示名称，解散则会在每个客户端上永久移除它——即使是当时离线的客户端——而重建一个同名群组则会开始一个全新的房间。如果某个网关宕机或被移除，什么都不会丢失：每个已连接的 Desktop 都在本地保留完整房间，并在重新连接时向任何网关重新播种。（完整的编排日志保留在每个 Desktop 的本地存储中；共享镜像只是一份有界的近期历史投影。）

群组与 Bot 私聊一样，都是按活动时间排序的名单中的独立行。一个 Bot 即使属于多个群组，也仍只保留一行私聊，而每个群组都有自己的房间行，包含成员数、最新消息预览、时间戳和 needs-you 状态。

使用房间旁边的 **Move up** 和 **Move down** 箭头来选择它在各房间中的位置。在第一次移动之前，现有置顶优先、近期活动的顺序保持不变。移动之后，房间顺序会保存在此 Desktop 上并在重新加载后保留；新房间会跟随已明确排序的房间，归入其置顶或非置顶的区间内。移动不能跨越置顶边界，筛选也不会把隐藏的房间从保存的顺序中丢弃。这些控件重排的是实际的群聊房间，而不是用户创建的 Bot 文件夹，也不会改变成员关系或网关归属。

对任意群组行（2–6 个 Bot）点击 **Open chat** 会打开一个共享房间，整个群组在其中协同：

- **一个可见的对话。**公开消息和每位成员的回复按到达顺序保持可读，并带有发言者姓名和时间戳。开启另一个话题不会收起之前的回复。**Reply in thread** 会延续该话题而不重排房间；**Activity** 是辅助的状态视图，而不是消息的替代品。私有的 Bot 聊天仍保持独立。
- 你的消息会触发最多**三轮串行的成员轮次**。被 @ 提及的 Bot 会响应（无人被提及时则所有人都响应）；每个 Bot 简短回复或选择跳过，当整整一轮都保持沉默时房间便归于平静。
- 队友可以用 `@hermes` 移交给主 Bot，包括在较旧的已保存房间中；位于其他网关上的 Bot 保留其带设备限定的标签（例如 `@default-vera`）。
- Bot 彼此之间用 `@name` 相互拉入，并把真正需要判断的事升级给你，方式是用 `@user`——发生这种情况时，群组行会显示一个 **needs you** 徽章。待处理的问题和命令批准也会点亮该徽章；解决最后一个提示只会清除提示相关的注意标记，而不会清除独立的提及。提示会跟随房间的重命名，而解散则会让它们失效，即使某个成员的在途轮询稍后到达。
- 硬性上限（每次发送 10 条消息、3 轮）可防止房间空转。
- 每个成员都保留自己持久的 `Group: <name>` 会话，因此房间上下文会像任何其他对话一样得以延续。
- **并非每个 Bot 都会回复每条消息。**是否发言由每个成员自行决定——Bot 只有在有新的内容可补充时才回复，否则就跳过，而 @ 提及特定成员会把该轮次限定在这些人身上。你所要预期的，是你 @ 到的成员（或任何有话可说的人）会发言，其余则保持安静。
- **你关闭 Desktop 后房间仍会继续运行。**当一个房间的所有成员都在同一个网关上时，该网关通过持久化驱动掌握轮次调度：关闭 Hermes Desktop（或断开其连接）不会让房间在讨论中途停止，Desktop 重新连接时只需从房间日志中追赶进度。网关上的 `groups.capabilities` 在适用时会报告 `driver: true`。成员分布在多台机器上的房间则不同：每个成员的轮次在其自己的网关上运行，而 *Bot 间消息传递*下描述的跨连接中转仍适用于它们。
- **房间可以跨越机器。**New Group Chat 选择器可以让来自任意已注册连接的 Bot 入座；每个成员的轮次都在其自己的机器上、其自己的 `Group: <name>` 会话中运行。跨机器成员会在房间中以及其他成员的记录中带上设备徽章（`dixie · Mac Mini`），而去歧义后的 `@name-device` 句柄在房间提及中也有效——因此两台机器上同名的智能体绝不会被混为一谈。
- **插件可以观察成员的工作过程。**持久化房间日志会记录 `turn.started` 和 `turn.settled`；成员在此期间所做的（工具调用、批准、流式文本）会通过 [`on_room_member_activity`](/user-guide/features/hooks#on_room_member_activity) 钩子投射给插件，并带有房间、成员和轮次坐标，因此社区客户端可以在群聊之上构建工具卡片和实时成员状态，而无需读取 Hermes 内部结构。

## Bot 间消息传递

Bot 之间带着归属信息互相发消息，你可以在任何对话中移交工作：

- **@mentions** —— 在任意对话中输入 `@researcher have a look at this`，输入框的 `@` 自动补全会帮你挑中正确的 Bot；发送时，该提及会对照实时名册进行解析，并明确告知当前活跃 Bot 你指的是谁（配置档、友好名称，以及跨连接 Bot 的设备）。随后该 Bot 会自己组织消息并通过 `message_agent` 发送——你的文字绝不会被逐字转发，回复会以该智能体为归属返回。电子邮件地址或未知的 `@` 会原样通过。位于其他已连接机器上的 Bot 也能以同样方式触达：Desktop 会通过该连接自己的套接字转发消息（见下文*跨机器的 Bots*）。
- **重命名的 Bot 会同步其标签** —— 给 Bot 起一个友好名称（在其对话标题栏中点击铅笔图标，或使用 `hermes profile rename`）后，它就能以该名称被提及：标题为 *Research Buddy* 的 Bot 会响应 `@research-buddy`（以及 `@researchbuddy`），无论常规对话还是群组房间中都是如此。输入框的 `@` 自动补全会给出重命名后的标签，当你输入旧的配置档名称时也能匹配，且旧名称仍可解析。
- **私信** —— 每个 Bot Chat 都带有 `message_agent` 工具：Bot 通过调用 `message_agent(target="researcher", message="…")` 给同伴发消息。该工具会对照实时名册验证目标，自动为发送者加上 `Message from 🤖 <sender> (@<sender>):` 归属前缀，并投递到该同伴的规范 Bot Chat 中。投递是**发射后不管**的：发送方会收到确认，结束本轮工作，回复稍后以后台完成通知的形式到达。消息以真实参数形式传输（不经任何 shell 解析——引号、`$(...)` 和反引号都原样抵达），且 Bot 会自己组织消息，而不是转发你的话。同伴名册——包含每个配置档标题/描述中的名称**与角色**——是每个 Bot Chat 系统提示词的一部分，因此 Bots 在选择收件人之前就知道谁负责什么。该工具**仅**存在于由 Bot 模式管理的安装中的规范 Bot Chat 会话里；常规对话、群组房间成员会话和 CLI 会话永远不会看到它。

本地消息也能触达在 Desktop 或 TUI 中保持打开的 Bot Chat。接收方后端保留所有权：它通过现有的通知轮询器读取持久化入站消息，空闲时立即接收，否则等待当前运行的一轮以及已排队的人类提示完成。`queued` 确认表示持久化接收，**而非**回复已完成。目标配置档把投递 ID 和回执保存在 `runtime/bot_live_delivery/` 下；`settled` 确认完成。导入的一轮若崩溃或被取消，不会自动重放，且固定到已离开拥有者的待处理工作仍可检查，而不会被静默重跑。对于结果未知的投递，不要重发。不具备实时投递能力的旧版后端仍保留原有的所有权拒绝行为；升级后请重启该后端。

后端在构建提示词时自动教会每个 Bot 的规范 Bot Chat 会话这套消息传递协议——包括同伴从 CLI 以无头模式打开它时也是如此。只有规范 Bot Chat 会获得协议段落；你的常规会话和 SOUL.md 不受影响。这由 `config.yaml` 中的 `agent.bot_mode_protocol` 控制（默认：开启）：

```yaml
agent:
  bot_mode_protocol: true   # inject the bot-to-bot messaging protocol into canonical Bot Chats
```

:::note
Bot 间投递是按调用进行的：接收方 Bot 在下次运行时才会取走消息。在对话中途实时打断 Bot 属于未来工作。
:::

### 失败的一轮会安全重试

本地一次性投递将活动会话拒绝码与其人类可读消息分开保存。`SESSION_NOT_OWNED` 会产生 `target_busy`；无法读取的协调注册表不会被错误标记为其他拥有者。没有该代码标记的旧版本地 CLI 仍使用历史上的拒绝措辞。

失败的一轮投递最多重试一次，且仅当重试确实能有所帮助时。瞬时失败（目标运行时离线、投递超时、服务商速率限制或服务端错误）会原样重新运行同一个 Bot Chat 会话。上下文溢出失败也会重新运行同一个会话——重试的这一轮会先通过标准上下文压缩流程压缩超过阈值的转录，再调用模型，因此重试能装下原本装不下的内容。认证、配额和配置失败从不自动重试：第二次尝试既无法修复它们，又只会消耗配额，因此失败会立即浮现。重试的一轮绝不会开启全新会话——你的 Bot Chat 历史和上下文保持完整。

当目标没有活跃的 Desktop 或 TUI 拥有者时，本地投递会通过一次静默 CLI 轮次打开该配置档的规范 Bot Chat。传输层优先选用发送方运行时 Python 解释器旁边的 Hermes 入口点，因此当这个同级入口点存在时，服务 `PATH` 上无关的或更旧的 `hermes` 无法抢先。`--in ~` 选择工作目录；显式的 Bot Chat 标题会在目标配置档的会话数据库中解析。

### 当投递失败时：带类型的失败原因

失败的 bot 回合或中继投递会沿着整条链路，在人类可读的错误文本旁携带一个机器可读的 `reason` 代码：目标网关对失败进行分类（`provider_auth_or_access`、`provider_quota_limit`、`provider_rate_limit`、`provider_server_error`、`context_overflow`、`missing_config`、`model_unavailable`、`runtime_offline`、`queued_expired`、`delivery_timeout`、`target_busy`、`unknown`），Desktop 转发该代码，而发送方智能体的完成通知会在错误文本之前被标记为 `[reason: <code>]`。调用方智能体可以基于该代码进行分支判断——“重新登录”还是“稍后重试”——而无须解析服务商的措辞。Desktop 的需关注徽标也使用相同的代码。

### 跨已连接机器收发消息（Desktop 中继）

你在 **设置 → 连接** 中注册的每个网关——本地、远程 URL、SSH、Hermes Cloud、docker——都是 Desktop 持续持有的一条常驻连接，Bot Mode 会自动使用这些连接收发消息。无需额外设置：

- **花名册自动传播。** Desktop 运行期间，会定期告知每个已连接的网关：*其他*连接上住着哪些智能体。于是每个 Bot Chat 的队友花名册都会列出它们（“其他已连接机器上的队友”），包含名称、角色以及它们所在的机器——当智能体出现、消失或被重命名时，花名册会自动刷新（能力纪元）。
- **`message_agent` 可直接联系它们。** 你笔记本上的 Bot 用 `message_agent(target="moxie", …)` 给云端智能体发消息，就和给本地队友发消息一模一样。如果同一个句柄存在于多台机器上，用 `target="moxie@<connection>"` 加以区分（该工具的错误信息会告诉 Bot 确切的形式）。投递经由 Desktop：发送方网关将消息入队，Desktop 将其中继到目标连接自己的网关，目标 Bot 在其规范 Bot Chat 中运行一个回合，回复再作为本地私信所用的同一类后台完成通知返回给发送方。
- **Desktop 是信使。** 只要有一个同时知晓这两个连接的 Desktop 在运行，跨连接投递就能工作（它持有套接字和凭据——各网关从不会看到彼此的身份验证）。如果 Desktop 在投递中途被关闭，发送方的 Bot 会被告知回复未能到达，而不是被一直挂着。对于无需 Desktop 介入的常开机器间消息收发，可注册一个对等端（`hermes peer`，见下文）——这两条路径可共存。

### Bot 发起的跨机器私信（`hermes peer`）

一台机器上的 Bot 可以直接给**另一台机器的网关**上的 Bot 发消息，无需任何 desktop 介入。将另一个网关注册为一个*对等端*（其 API 服务器 URL + `API_SERVER_KEY`）：

```bash
hermes peer add spark --url http://spark.lan:8377 --key <API_SERVER_KEY>
hermes peer list
hermes peer dm spark < /tmp/dm.txt        # message body from a file (nothing shell-interpreted)
hermes peer dm spark/researcher < /tmp/dm.txt   # named profile on a multiplexed peer
hermes peer run spark --idempotency-key ticket-123 < /tmp/long-task.txt
hermes peer status spark run_abc123
hermes peer stop spark run_abc123
```

`hermes peer dm` 会经由对等端现有的 API 服务器将消息投递到远程智能体的规范 Bot Chat，在那里运行一个智能体回合，并在 stdout 上打印回复——它正是本地 `hermes -p <bot> chat` 命令在跨机器场景下的精确对应物。

只在短查询和回执中使用 `peer dm`，因为它会一直占用一条 HTTP
连接，直到该回合结束。对于长回合，`peer run` 会立即返回一个
`run_id`；用 `peer status` 轮询它。该运行会继承
规范 Bot Chat 的记录，一个稳定的 `--idempotency-key` 能让重试
返回原来的运行，而不是启动重复的工作。使用 `peer stop`
搭配那个确切的 run ID 来中断它，而不会误伤另一个回合。

一旦注册了对等端，教授给每个 Bot Chat 的消息协议（`agent.bot_mode_protocol`）便会自动包含对等端花名册，且 `message_agent` 直接接受对等端目标——`message_agent(target="spark/researcher", …)`，或者 `target="spark"` 指向对等端的主智能体——因此**你的 bot 会自行得知**其他机器上存在队友以及如何联系它们。注册或移除对等端会在每个 Bot Chat 的下一条消息时刷新其协议（能力纪元）。

要求：对等端机器需运行 `api_server` 网关平台并配置一个强度足够的 `API_SERVER_KEY`；可达性是你们网络自己的事（局域网、Tailscale、VPN）。该密钥是一种凭据，存放于 `~/.hermes/.env` 中，名为 `HERMES_PEER_<NAME>_KEY`；对等端的名称/URL 存放在 `config.yaml` 的 `bot_peers` 下。

:::note 单向可达性（NAT）
跨网关链路是直接的网关到网关连接——Desktop 是查看器，不是中继。
位于家庭 NAT 之后的网关可以向外拨号连接到一个公网对等端
（笔记本 → VPS 可行），但反方向没有入站路由
（VPS → 家庭网络会失败），除非你们的网络提供了这样一条路由。如果你的 Group Chat 跨越
NAT 边界，请把房间的权威放在每个参与者都能
触达的主机上（通常是公网 VPS），或者用 Tailscale/VPN 打通网络。
:::

### 转移托管房间权限

权限接管是**运维人员的恢复流程**，不是原子化交接。
在适当的网关上使用现有的 JSON-RPC 方法 `groups.promote` 和 `groups.demote`。
不存在 `groups.peer.promote` 或 `groups.peer.demote` 方法；`groups.capabilities` 会列出你的网关所支持的方法。

:::warning 在提升之前先隔离旧写入方
在发送 `confirm: true` 之前，必须确证先前的权威**无法提交**，并且在这个隔离生效期间保持有效，直到它被降级。停止其房间写入进程并阻止自动重启，或采用等效的基础设施隔离手段。网络超时、断开桌面端，或 `groups.stop` 都不构成证据：旧的网关可能仍在运行，而停止一个回合并不会撤销房间权限。如果你无法建立隔离，就不要提升。
:::

1. **检查副本覆盖情况。** 在替换网关上，用 `{"room_id":"ROOM_ID"}` 检查
   `groups.replica_state`，并将 `last_seq` 与 `latest_seq` 进行比较。计划内接管要求完整的副本；
   提升本身并不会检查此覆盖情况。`groups.replicate` 在摄取 `groups.log`
   返回的页面后报告 `caught_up`；仅凭对等注册不能证明替换方拥有房间历史。
   已同步状态描述的是最后复制的页面，而不是证明旧的写入方已停止或不存在更新的事件。
   对于计划内迁移，先静默写入方，复制到最后一条游标，然后维持隔离。
   对于灾难恢复，把从未到达副本的任何历史也考虑在内。
2. **只有在旧写入方被隔离时才能提升。** 在替换方上：

   ```json
   {"jsonrpc":"2.0","id":1,"method":"groups.promote","params":{"room_id":"ROOM_ID","confirm":true,"reason":"planned-handover"}}
   ```

   `room_id` 和 `confirm: true` 为必填；`reason` 是可选的，默认为
   `authority-unreachable`。确认是你断言先前的权威无法提交，**而不是**
   让它自动被隔离的请求。没有确认时调用会返回错误 `4118`。成功的结果会报告
   `authority_gateway_id` 和 `authority_epoch`（复制的 epoch 加一）。
3. **在将旧权限重新投入使用之前先将其降级。** 在旧网关上通过受控的恢复连接
   应用此 RPC 时，保持其常规房间写入方处于隔离状态。用成功提升返回的
   确切值替换示例中的网关 ID 和 epoch：

   ```json
   {"jsonrpc":"2.0","id":2,"method":"groups.demote","params":{"room_id":"ROOM_ID","observed_gateway_id":"NEW_GATEWAY_ID","observed_epoch":2}}
   ```

   三个参数均为必填。不要猜测一个未来的 epoch：降级需要更新权威的证据，
   而不是编造的值。它会记录 `authority.lost` 并采纳所观察到的血缘；重复同一血缘
   是幂等的。如果旧主机不可用，将其保持隔离，并在恢复正常写入方之前执行此步骤。
4. **验证并重新连接。** 在两个网关上读取 `groups.state`，将
   `room.authority_gateway_id` 和 `room.authority_epoch` 与提升结果进行比较。
   旧权威的发送必须被拒绝；将客户端引导至替换方。
   降级会隔离写入；它不会合并历史，也不会自动将旧的权威存储转变为同步副本。

如果旧网关仍可写时进行提升，会让两个独立的
`state.db` 存储都接受消息并产生分歧历史。替换方上更高的 epoch 无法远程禁用旧写入方；
对于脑裂并不要求 epoch 相等。如果历史已经分歧，请隔离写入方并为双方保留历史以便恢复，
而不是假设提升、降级或重放会将它们合并。

## 跨机器的机器人

当你在 **设置 → 连接** 中注册多个后端时——本地运行时、远程网关、SSH 主机、Hermes Cloud 实例——
名册会持久地显示来自**每个**已连接来源的机器人：SSH 来源会进行清点而不会在远程计算机上启动任何进程，
瞬间不可达的机器会保留其最后已知的记录行，而不是消失。当相同的配置档名称出现在多个来源上时，
句柄会以 `@name-device` 消歧（例如 `@research-homelab`）。机器人的聊天、会话、记忆和例程存在于拥有该配置档的那台机器上。

点击“连接”中的机器人**不会**把你的窗口跳转到那台机器——请留在你的聊天中并通过 `@提及` 它，
将其安置到群聊中，或者用 **在……上创建** 选择器直接在其上创建新的智能体。云和本地智能体
因此共享同一份名册：注册你的 Hermes Cloud 实例和你的桌面端（比如，通过 Tailscale 或 SSH），
它们的机器人便可以互相发消息并坐在同一个房间里，而每个智能体的工作会在各自的机器上运行。
跨这些机器的机器人对机器人私信会自动经过桌面端中继（参见上文*跨已连接机器传递消息*）。

关于完整的多连接指南，请参见[将桌面端连接到多个 Hermes 实例](./multi-connection-desktop.md)。

## 热机器人后端（同时运行多少个机器人）

每个本地机器人都在自己的后端进程中运行，桌面端在任一时刻最多保持 **设置 → 高级 → 热机器人后端**
数量的此类进程存活（默认 3 个，每个约 60 MB）。空闲后端会在该设置旁的空闲超时后
被回收（默认 10 分钟）；`desktop.log` 中伴随空闲回收消息出现的
`Hermes backend for profile "<name>" exited (1)` 行是这种清理，而不是崩溃。
如果每个槽位都被占用时你打开一个机器人，它会等待最多 30 秒以获得槽位，
随后失败并报 *等待可用的本地槽位超时*。

读取另一个机器人的聊天记录以及后台转录刷新**不会**占用槽位——只有交互式打开或
一个正在运行的回合才会占用。如果你驱动大规模机群（成员众多的群聊，或跨多个配置档的
看板派发），请将热机器人后端提高到你需要同时活跃的机器人数量，
并为机器配备与之匹配的内存。将其设置得高于你实际使用的配置档数只会增加启动工。

## 将其关闭

机器人模式是一个捆绑的桌面插件。在 **能力 → 插件 → 机器人** 中关闭其 **桌面** 开关——
名册、例程窗格和输入框中间件会即时注销，无需重启。你的配置档、会话和定时任务
无论哪种方式都不受影响；机器人模式从不拥有你的数据，它只是渲染它。

还有一个偏好设置可以隐藏常规侧栏会话列表中的规范机器人聊天，
让它们只出现在机器人窗格内。（这使用的是核心的隐藏会话标志；在较旧的网关上，这些聊天仍会保持可见。）
