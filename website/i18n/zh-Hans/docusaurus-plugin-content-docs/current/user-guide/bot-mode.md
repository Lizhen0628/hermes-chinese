# Bot 模式

**Bot 模式**将你的 [Hermes 配置档](./profiles.md)变成一组具名 **Bot** 的花名册。每个 Bot 都有自己的角色、模型、记忆、技能和头像；Bot 可以运行周期性例程、在群聊中共同商议，并直接互相发送消息。构建一个专家 Bot 一次，它就永远在那里，只需点击一下即可。

Bot 模式**内置在[桌面应用](./desktop.md)中**，并且**默认开启**——无需安装。它作为左侧边栏中 Sessions 旁边的 **Bots** 标签页出现，当 Bots 标签页处于活动状态时，一个 **群组例程** 磁贴停靠在对话旁边。

:::tip Bot 就是一个配置档
没有新的原始概念需要学习：Bot **就是**一个 Hermes 配置档——隔离的配置、记忆、技能、凭据和聊天历史都位于 `~/.hermes/profiles/<name>/` 下。Bot 模式是建立在这个原始概念之上的 UI，因此你在其中所做的一切从 CLI 中也能看到：`hermes -p <bot> chat` 打开的是同一个智能体，Bot 例程会出现在 `hermes cron list` 中。没有核心补丁，没有后台守护进程，没有额外存储。
:::

## Bots 面板

花名册为每个智能体配置档显示一行：头像、最新消息预览和时间戳。

- **点击一个 Bot** 进入其聊天——每个 Bot 都有一个规范的、持久的 **Bot 聊天** 对话，在 Bot 诞生那一刻就已创建（并固定）。点击行总是打开该 Bot 聊天（即行预览的同一对话），即使你为该 Bot 打开了其他标签页；那些标签页会保留在其旁边。在标签栏中，Bot 聊天以 Bot 的名称作为标题，因此两个打开的 Bot 一眼就能区分。
- **活跃显示**——花名册的活动过滤器包含聚焦实时回合的所有者、过去 90 秒内写入的 Bot，以及最近有工作进程心跳的 Bot。仅一个有连接的网关并不意味着一个 Bot 正在工作。
- **搜索**在你输入时过滤花名册。
- **隐藏一个 Bot**——右键单击一行 → **隐藏 Bot**，将你不使用的 Bot 从花名册和活跃显示条中移除。隐藏只影响显示：@提及仍然解析，群聊成员关系不受影响，例程继续运行。一旦至少隐藏了一个 Bot，面板标题中会出现一个**眼睛切换按钮**——点击它以淡显的方式在原位显示隐藏的 Bot，然后右键单击 → **取消隐藏 Bot** 将其恢复。隐藏的 Bot 从不会弹出提示，但它们会静默累积未读活动，眼睛图标会显示一个点，这样你就知道发生了事情。隐藏状态保存在 Bot 的配置档元数据中，因此它会跟随该 Bot 到连接到该后端的每个桌面上。

:::note 规范的 Bot 聊天是一个永久聊天
在 Bot 的规范聊天中输入 `/new`（或 `/reset`）会将关系分叉成一个临时会话——这是 Bot 模式承诺永远不会发生的唯一一件事。编辑器会将它重新路由到 `/compact`：全新的工作上下文，同一个对话。同一配置档上的常规会话保留完全的 `/new` 自由。
:::

### 将 Bot 分组到分区中

分区是你自己创建的文件夹——**客户**、**团队**，任何适合的——作为自动按网关分组旁边的第二个轴线。如果未创建分区，花名册就是你一贯使用的普通列表。

- **创建一个分区**：从面板的 **+** 菜单 → **新建分区**，或右键单击一个 Bot → **移动到分区** → **新建分区……**（在创建分区的同时将该 Bot 归入其中）。
- **归档一个 Bot**：将其行拖到一个分区上——悬停时目标会高亮，**Esc** 可取消拖动——或右键单击 → **移动到分区**并选择一个。**从分区中移除**将其放回 **未分配**。
- **重命名、重新排序或删除一个分区**：从分区标题的右键单击菜单（或悬停时出现的 **⋯**）；双击标题可重命名。标题可以像网关标题一样折叠。
- **删除分区永远不会删除 Bot**——它们会回到 **未分配**，并且提示会提供 **撤销**。不会询问确认。

成员关系存储在每个 Bot 的配置档元数据（`ui_meta`）中，因此 Bot 的分区会跟随它到连接到该后端的每个桌面。当花名册显示多个网关时，分区嵌套在每个网关的桶内。

## 创建一个 Bot

在花名册中点击 **新智能体**。快捷路径是三个字段——**名称**、**标题**、**描述**——Bot 在几秒内就存在了，并以其新 Bot 聊天的第一条消息自我介绍。

一个**高级**展开项打开完整的能力界面：

- **从现有配置档克隆**——从另一个 Bot 的配置、技能、SOUL 和记忆开始，或选择 **全新配置档** 干净开始。
- **创建空配置档**——完全跳过捆绑技能，得到一个最小化的配置档。
- **模型和服务商固定**——给 Bot 它自己的模型。Hermes 已知的任何服务商/模型配对都可用，不同的 Bot 可以并排运行在不同的模型上。保持未设置以继承启动配置档。
- **自定义 SOUL.md**——Bot 的角色设定和常设指令。
- **逐技能、逐工具集和逐 MCP 服务器的启用**——精确勾选该专家所需的能力。
- **共享密钥**——默认情况下，新 Bot 与主配置档共享一个 OAuth/令牌池，因此凭据刷新不会使彼此无效。（较旧的网关改为复制凭据——仍然可用，只是分叉了。）

### 选择它生活在哪台机器上（"创建于"）

当 [设置 → 连接](./multi-connection-desktop.md)中注册了多个连接时，新建智能体对话框会多出一个 **创建于** 选择器。选择一个设备，配置档就在**那台**机器的后端上创建——你的窗口永远不会切换网关。新 Bot 随后在花名册中显示为一个连接 Bot（当名称存在于多台机器上时带有 `@name-device` 句柄），与其聊天会路由到它自己的机器。

只有一个连接（常见情况）时，该选择器隐藏，Bot 创建在你所连接的机器上——与旧行为完全相同。

远程创建说明：

- **克隆源**是*目标*机器的配置档（其 `default`）——远程机器没有你的本地配置档可克隆。
- 实时能力标签页固定到目标机器的后端，因此你在创建期间配置的技能、工具和 MCP 服务器会落在该 Bot 将生活的机器上。（较旧的桌面构建对于远程目标回退到分阶段的技能/工具/MCP 检查清单；两者都读取目标机器的目录。）
- 取消对话框会丢弃它在哪台机器上创建的草稿配置档。

**编辑配置档**（右键单击一个 Bot）随时在实时配置档上重新打开同一界面：头像、标题、描述、模型固定、技能、工具集、MCP 服务器以及完整的 SOUL.md。

**复制**（右键单击）对一个 Bot 进行完整克隆——配置、技能、SOUL.md、记忆及其外观。**删除配置档**永久移除一个，位于桌面配置档菜单所用的同一破坏性确认之后；默认配置档无法删除。

## 头像

每个 Bot 都有一张脸：

- **团块面孔**（默认）——一种根据 Bot 名称绘制的确定性软体面孔：相同的名称，相同的面孔，永远如此。当你在新建智能体中输入名称时，面孔会实时跟随它；点击 **随机** 重新抽取，**锁定面孔** 保留你喜欢的那一个即使名称改变，或固定六个剪影之一（圆形、有机、方正、结节、云形、太阳形），同时其他一切仍然来自名称。
- **几何面孔**——经典的 7 种形状 × 10 种颜色。在一个聚焦的实时回合期间，拥有该回合的 Bot 会倾斜并向上看，带有三个动画点，然后在该回合结束时缓动回到静止状态。所有权包含连接，所以不同网关上的同名 Bot 不会借用姿势。后台工作者保留其现有的工作动画；照片、团块面孔和印记保留它们自己的渲染方式。
- **一张上传的图片**——你喜欢的任何图片。
- **一张 AI 生成的肖像**——当配置了图像后端时，就地生成（这使用标准的 `image.generate` RPC，在本地和远程网关上都能工作）。
- **一个像素宠物**——来自[宠物图库](./features/pets.md)的伙伴，在 Bot 忙碌时在头像旁边跳跃。在终端运行 `hermes pets` 来探索图库。

Bot 的外观、标题和描述存储在后端上配置档的元数据中，因此同一个 Bot 在连接到该后端的每个桌面上以相同方式出现。

## 例程

**例程**窗格将周期性任务附加到执行它们的 Bot 上——"每天早上总结我的收件箱"就与负责它的 Bot 在一起。该窗格只在你停留于 Bots 标签页时停靠在聊天旁边，当你切换回 Sessions 时退出（较旧的桌面构建中它会始终可见）。一个结构化调度选择器构建调度（先频率，然后只选重要的细节），一个高级字段暴露原始的 Hermes 调度字符串。

例程就是普通的[智能体定时任务](./features/cron.md)，命名空间为 `[bot:<name>] <routine>`——它们也会出现在 `hermes cron list` 和核心 Cron 页面中。运行结果落在 Bot 自己的聊天历史中，所以结果就在你与该 Bot 交谈的地方。

## 群组和群聊

在成员回合期间发送的消息排在活动房间驱动的后面，包括同一话题中的回复。它们不会打断该成员，也不标记未见消息为已读。停止会取消排队的延续，并扣留成员直到恢复。一个安静的房间在其前台等待结束后还会再观察超时成员 21 分钟；这个观察窗口不会延长回合本身。未解决的成员失败在房间安定后仍保留在折叠的 Activity 总结中可见。展开 Activity 查看回合序列；重新针对该成员发话以重试。有歧义的提交失败不会自动重新提交。


右键单击一个本地 Bot → **管理群组** 将其添加到任意数量的群聊中或从中移除。独立选择现有群组或内联创建一个。本地成员关系存储在 Bot 的后端同步的配置档元数据中，因此它会跟随该配置档跨桌面；带有单个旧群组的较旧配置档继续工作。连接 Bot 通过"新建群聊"选择器加入，并在房间的共享状态中保持来源限定。

**房间跟随你的网关，而不是某个桌面。**每个房间的近期记录、成员、图片和名称都被镜像到你的桌面所连接的**每个**网关的共享配置档元数据中，并带有逐网关版本控制，从而使两个桌面同时写入时合并而非互相覆盖。在另一台机器上针对同一网关打开 Hermes Desktop（本地网络、Tailscale，任何地方），房间就会带着它的历史出现；仅网关的客户端也能看到它。房间拥有一个持久的内部身份，因此重命名一个房间仅在所有地方改变其显示名称，解散一个房间会在每个客户端上永久移除它——即使当时离线的客户端也是——重新创建一个同名的群组会启动一个真正全新的房间。如果一个网关崩溃或被移除，什么都不会丢失：每个已连接的 Desktop 在本地保留完整的房间，并重新播种它所重新连接的任何网关。（完整的编排日志保留在每个 Desktop 的本地存储中；共享镜像是有限制的近期历史投射。）

群组是同一个按活动排序的花名册（与 Bot DM 相同）中的独立行。一个 Bot 即使属于多个群组也只会保留一行 DM，而每个群组都会获得自己的房间行，带有成员数量、最新消息预览、时间戳和需要你状态。

使用一个房间旁边的 **上移** 和 **下移** 箭头来选择它在房间中的位置。在第一次移动之前，现有的固定优先、按近期活动的顺序不变。移动后，房间顺序保存在本 Desktop 上并能在重新加载后保持；新房间在其固定或未固定的带中遵循显式排序的房间。移动不能越过固定边界，过滤不会将隐藏房间从保存的顺序中丢弃。这些控件重新排序的是实际的 Group Chat 房间，不是用户创建的 Bot 文件夹，不会改变成员关系或网关所有权。

任何群组行上的 **打开聊天**（2–6 个 Bot）打开一个共享房间，整个群组在此协调：

- **一个可见的对话。**公开消息和每个成员的回复按到达顺序可读，带有说话者名称和时间戳。开始另一个话题不会折叠更早的回复。**在话题中回复**延续该话题而不重新排序房间；**Activity** 是一个次要的状态视图，不是消息的替代品。私有 Bot 聊天保持独立。
- 你的消息触发最多**三轮串行**的成员回合。被 @提及的 Bot 回应（当没有人被提及时，所有人都回应）；每个 Bot 简要回复或跳过，当一个完整轮次保持沉默时房间安定下来。
- 队友可以移交到主要 Bot，使用 `@hermes`，包括在较旧的已保存房间中；其他网关上的 Bot 保留其带设备限定的标记（例如，`@default-vera`）。
- Bot 用 `@name` 互相拉入，并用 `@user` 将真正的判断决定升级给你——当发生这种情况时，群组行会显示一个 **需要你** 标记。待处理问题和命令审批也会点亮该标记；解决最后一个提示只清除提示关注，不清除一个独立的提及。提示跟随重命名后的房间，而解散会使其退役，即使某个成员的进行中轮询稍后到达。
- 硬性上限（每次发送 10 条消息，3 轮）防止房间空转。
- 每个成员保留自己的持久 `Group: <name>` 会话，因此房间上下文像任何其他对话一样留存。
- **不是每个 Bot 都回复每条消息。**发言是每个成员自己的选择——一个 Bot 仅在它有新的内容要补充时才回复，否则跳过；@提及特定成员将轮次限定在他们身上。期望你针对的成员（或有话要说的人）发言，其余保持安静。
- **你关闭 Desktop 时房间继续运行。**当一个房间的每个成员都生活在同一个网关上时，该网关通过一个持久驱动拥有回合调度：关闭 Hermes Desktop（或失去其连接）不会在讨论中途停止一个房间，Desktop 在重新连接时简单地从房间日志中追赶过来。当适用时，网关上的 `groups.capabilities` 报告 `driver: true`。成员跨越几台机器的房间则不同：每个成员的回合在其自己的网关上运行，*Bot 间消息传递*下描述的跨连接信使仍然适用于它们。
- **房间可以跨越机器。**新建群聊选择器可以从任何注册的连接中安排 Bot；每个成员的回合在其自己的机器上运行，在那里其自己的 `Group: <name>` 会话中。跨机器成员在房间中和其他成员的记录中带有一个设备徽章（`dixie · Mac Mini`），消歧的 `@name-device` 句柄在房间提及中有效——所以两台机器上的同名智能体永远不会模糊在一起。
- **插件可以观察成员工作。**持久的房间日志记录 `turn.started` 和 `turn.settled`；一个成员在此之间所做的事情（工具、审批、流式文本）通过 [`on_room_member_activity`](/user-guide/features/hooks#on_room_member_activity) 钩子投射给插件，带有房间、成员和回合坐标，因此社区客户端可以在 Group Chat 之上构建工具卡片和实时成员状态，而无需阅读 Hermes 内部。

## Bot 间消息传递

Bot 之间有溯源地互相发送消息，你可以从任何聊天中移交工作：

- **@提及**——在任何聊天中输入 `@researcher have a look at this`，编辑器中的 `@` 自动补全帮助你选择正确的 Bot；发送时，提及会根据实时花名册解析，活动 Bot 会被告知你确切指的是谁（配置档、友好名称，对于跨连接 Bot 还包括设备）。然后该 Bot 撰写自己的消息并用 `message_agent` 发送它——你的文本永远不会被逐字转发，回复带着该智能体的溯源返回。一个电子邮件地址或未知的 `@` 原样通过。其他已连接机器上的 Bot 以相同方式可达：Desktop 通过该连接自己的套接字转发消息（见下方*跨机器的 Bot*）。
- **重命名的 Bot 保持其标记同步**——给一个 Bot 一个友好名称（其聊天标题栏中的铅笔，或 `hermes profile rename`），它就可以通过该名称被标记：标题为 *Research Buddy* 的 Bot 会响应 `@research-buddy`（以及 `@researchbuddy`），在常规聊天和群组房间中都是如此。编辑器中的 `@` 自动补全提供重命名后的标记，并且在你输入旧配置档名称时也匹配，而旧名称仍然解析。
- **直接消息**——每个 Bot 聊天都携带 `message_agent` 工具：Bot 通过调用 `message_agent(target="researcher", message="…")` 给队友发消息。该工具会根据实时花名册验证目标，自动加上发送者的 `Message from 🤖 <sender> (@<sender>):` 溯源前缀，并投递到队友的规范 Bot 聊天中。投递是**发后即忘**：发送者收到确认，完成其回合，回复稍后作为后台完成通知到达。消息作为真实参数传输（没有 shell 解释——引号、`$(...)` 和反引号原样到达），Bot 撰写自己的消息而非转发你的话。队友花名册——**名称和角色**来自每个配置档的标题/描述——是每个 Bot 聊天系统提示的一部分，因此 Bot 在选择收件人之前就知道谁做什么。该工具**只**存在于 Bot 模式管理的安装上的规范 Bot 聊天会话中；常规聊天、群组房间成员会话和 CLI 会话从不会看到它。

本地消息也会到达在 Desktop 或 TUI 中保持开放的 Bot 聊天。接受后端保持所有权：它在其现有的通知轮询器上读取持久入口，在空闲时立即接收，或等待运行中的回合和已排队的人类提示完成。一个 `queued` 确认确认了持久接收，**而非**完成的回复。目标配置档在 `runtime/bot_live_delivery/` 下保留投递 ID 和回执；`settled` 确认完成。一个崩溃或取消的导入回合不会自动重放，固定到已离开的所有者的待处理工作仍然可检查，而不会被静默重跑。不要重发结果未知的投递。没有实时投递能力的较旧后端保留现有的所有权拒绝；升级后重启该后端。

后端在提示构建时自动教每个 Bot 的规范 Bot 聊天会话该消息传递协议——包括当队友从 CLI 中无头地打开它时。只有规范 Bot 聊天会获得协议部分；你的常规会话和你的 SOUL.md 保持原样。这由 `config.yaml` 中的 `agent.bot_mode_protocol` 控制（默认：开）：

```yaml
agent:
  bot_mode_protocol: true   # 将 bot 间消息传递协议注入规范 Bot 聊天
```

:::note
Bot 间投递是按调用的：接收 Bot 在下次运行时拾取消息。在对话中途实时打断 Bot 是未来的工作。
:::

### 失败的回合安全重试

本地一次性投递将活动会话拒绝代码与其人类可读的消息分开保存。`SESSION_NOT_OWNED` 产生 `target_busy`；不可读的协调注册表不会被错误地标记为另一位所有者。没有代码标记的较旧本地 CLI 仍然使用历史拒绝措辞。

一个失败的投递回合至多重试一次，并且仅当重试确实可能有帮助时。瞬时失败（目标运行时离线、投递超时、服务商速率限制或服务器错误）会原样重跑同一个 Bot 聊天会话。上下文溢出失败也会重跑同一会话——重试的回合在调用模型之前通过标准上下文压缩通道压缩超阈值的记录，因此重试能装下原本装不下的内容。认证、配额和配置失败从不自动重试：第二次尝试无法修复它们，只会烧配额，所以失败会立即浮出。重试的回合从不启动新会话——你的 Bot 聊天历史和上下文保持完整。

当一个目标没有实时的 Desktop 或 TUI 所有者时，本地投递通过一个安静的 CLI 回合打开该配置档的规范 Bot 聊天。传输优先选择位于发送运行时的 Python 解释器旁边的 Hermes 入口点，因此服务 `PATH` 上无关的或较旧的 `hermes` 无法在该兄弟入口点存在时占据优先。`--in ~` 选择工作目录；显式的 Bot 聊天标题在目标配置档的会话数据库中解析。

### 当投递失败时：带类型的理由

一个失败的 bot 回合或中继投递端到端地带有一个机器可读的 `reason` 代码，伴随人类错误文本：目标网关对失败进行分类（`provider_auth_or_access`、`provider_quota_limit`、`provider_rate_limit`、`provider_server_error`、`context_overflow`、`missing_config`、`model_unavailable`、`runtime_offline`、`queued_expired`、`delivery_timeout`、`target_busy`、`unknown`），Desktop 转发它，并且发送智能体的完成通知在错误文本之前被标记为 `[reason: <code>]`。调用智能体可以基于代码分支——"再次登录"与"稍后重试"——而不是解析服务商的文字。Desktop 的需要关注标记使用相同的代码。

### 跨已连接机器的消息传递（Desktop 中继）

你在 **设置 → 连接** 中注册的每个网关——本地、远程 URL、SSH、Hermes Cloud、docker——都是 Desktop 保持开放的一条持久线路，Bot 模式自动使用这些线路进行消息传递。无需额外设置：

- **花名册自行传播。**Desktop 运行时，它定期告诉每个已连接的网关哪些智能体生活在*其他*连接上。然后每个 Bot 聊天的队友花名册会列出它们（"其他已连接机器上的队友"），带有名称、角色，以及它们在哪台机器上——当智能体出现、消失或被重命名时，花名册会刷新（能力纪元）。
- **`message_agent` 直接到达它们。**你笔记本电脑上的一个 Bot 用 `message_agent(target="moxie", …)` 给云上智能体发消息，就像本地队友一样。如果同一个句柄存在于多台机器上，用 `target="moxie@<connection>"` 消歧（该工具的错误会告诉 Bot 确切的格式）。投递经由 Desktop：发送网关排队消息，Desktop 将它中继到目标连接自己的网关，目标 Bot 在其规范 Bot 聊天中运行一个回合，回复作为本地 DM 所用的同一个后台完成通知回到发送者。
- **Desktop 是信使。**只要一个知道两个连接的 Desktop 正在运行，跨连接投递就能工作（它持有套接字和凭据——网关从不见到彼此的认证）。如果 Desktop 在投递中途关闭，发送者的 Bot 会被告知回复没有到达，而不是被吊着。对于没有 Desktop 参与的始终在线的机器对机器消息传递，注册一个对等端（`hermes peer`，见下文）——这两条路线共存。

### Bot 发起的跨机器 DM（`hermes peer`）

一台机器上的 Bot 可以向**另一台机器的网关**上的 Bot 发消息，无需任何桌面参与。将另一个网关注册为*对等端*（其 API 服务器 URL + `API_SERVER_KEY`）：

```bash
hermes peer add spark --url http://spark.lan:8377 --key <API_SERVER_KEY>
hermes peer list
hermes peer dm spark < /tmp/dm.txt        # 消息正文来自文件（无 shell 解释）
hermes peer dm spark/researcher < /tmp/dm.txt   # 多路复用对等端上的具名配置档
hermes peer run spark --idempotency-key ticket-123 < /tmp/long-task.txt
hermes peer status spark run_abc123
hermes peer stop spark run_abc123
```

`hermes peer dm` 通过对等端现有的 API 服务器投递到远程智能体的规范 Bot 聊天，在那里运行一个智能体回合，并在 stdout 上打印回复——本地 `hermes -p <bot> chat` 命令的精确跨机器对应物。

仅将 `peer dm` 用于短查询和回执，因为它会保持一个 HTTP 连接直到回合完成。对于长回合，`peer run` 立即返回一个 `run_id`；用 `peer status` 轮询它。该运行继承规范 Bot 聊天记录，一个稳定的 `--idempotency-key` 使重试返回原始运行而非启动重复工作。用那个确切的运行 ID 使用 `peer stop` 打断它，而不会针对另一个回合。

一旦一个对等端被注册，教给每个 Bot 聊天的消息传递协议（`agent.bot_mode_protocol`）会自动包含对等端花名册，并且 `message_agent` 直接接受对等端目标——`message_agent(target="spark/researcher", …)`，或对等端主要智能体用 `target="spark"`——所以**你的 bot 会自行知道**队友存在于其他机器上以及如何到达它们。注册或移除一个对等端会在其下一条消息时刷新每个 Bot 聊天的协议（能力纪元）。

要求：对等机器运行 `api_server` 网关平台并使用强 `API_SERVER_KEY`；可达性是你网络的事情（LAN、Tailscale、VPN）。该密钥是一个凭据，位于 `~/.hermes/.env` 中作为 `HERMES_PEER_<NAME>_KEY`；对等端名称/URL 位于 `config.yaml` 中的 `bot_peers` 下。

:::note 单向可达性（NAT）
跨网关链接是直接的网关对网关连接——Desktop 是查看器，不是中继。家庭 NAT 后面的网关可以拨出到一个公共对等端（笔记本电脑 → VPS 可行），但反向没有入站路由（VPS → 家庭失败），除非你的网络提供了路由。如果你的 Group Chat 跨越 NAT 边界，将房间的权威放在每个参与者都能到达的主机上（通常是公共 VPS），或用 Tailscale/VPN 桥接网络。
:::

### 转移托管房间的权威

权威接管是一个**操作员恢复程序**，不是原子移交。
在适当的网关上使用现有的 JSON-RPC 方法 `groups.promote` 和 `groups.demote`。
不存在 `groups.peer.promote` 或 `groups.peer.demote`
方法；`groups.capabilities` 列出你的网关支持的方法。

:::warning 在提升前隔离旧写入者
在发送 `confirm: true` 之前，确认前一个权威**无法提交**，并保持该隔离直到它已被降级。停止其房间写入进程并防止自动重启，或使用等效的基础设施隔离。网络超时、断开 Desktop 或 `groups.stop` 都不是证据：旧网关可能仍在运行，停止一个回合不会撤销房间权威。如果你无法建立隔离，不要提升。
:::

1. **检查副本覆盖情况。**在替换网关上，用 `{"room_id":"ROOM_ID"}` 检查 `groups.replica_state`，并将 `last_seq` 与 `latest_seq` 比较。有计划接管之前要求一个完整的副本；提升本身不检查此覆盖情况。`groups.replicate` 在摄取 `groups.log` 返回的页面后报告 `caught_up`；仅对等端注册并不能证明替换方拥有房间历史。已追赶状态描述的是最后复制的页面，不是旧写入者已停止或不存在更新事件的证明。对于计划内迁移，静止写入者，复制到最后游标，然后维持隔离。对于灾难恢复，考虑任何从未到达副本的历史。
2. **仅在旧写入者被隔离时提升。**在替换方上：

   ```json
   {"jsonrpc":"2.0","id":1,"method":"groups.promote","params":{"room_id":"ROOM_ID","confirm":true,"reason":"planned-handover"}}
   ```

   `room_id` 和 `confirm: true` 是必需的；`reason` 是可选的，默认
   为 `authority-unreachable`。确认是你关于前一个
   权威无法提交的断言，**不是**自动隔离它的请求。没有
   确认的调用返回错误 `4118`。成功结果报告
   `authority_gateway_id` 和 `authority_epoch`（复制的纪元加一）。
3. **在旧权威恢复服务前降级它。**在通过旧网关上受控的恢复连接应用此 RPC 时，保持其正常的房间写入者被隔离。用成功提升返回的确切值替换示例网关 ID 和纪元：

   ```json
   {"jsonrpc":"2.0","id":2,"method":"groups.demote","params":{"room_id":"ROOM_ID","observed_gateway_id":"NEW_GATEWAY_ID","observed_epoch":2}}
   ```

   所有三个参数都是必需的。不要猜测未来的纪元：降级
   需要更新权威的证据，而不是一个虚构的值。它记录
   `authority.lost` 并采纳观察到的谱系；重复同一谱系
   是幂等的。如果旧主机不可用，保持它被隔离并在恢复其正常写入者
   之前执行此步骤。
4. **验证并重新连接。**在两个网关上读取 `groups.state` 并将
   `room.authority_gateway_id` 和 `room.authority_epoch` 与提升
   结果比较。旧权威的发送必须被拒绝；引导客户端到替换方。
   降级隔离写入；它不会合并历史或自动将
   旧的权威存储转变为同步副本。

在旧网关仍可写时提升，允许两个独立的
`state.db` 存储都接受消息并发展出分歧的历史。替换方上更高的
纪元不会远程禁用旧写入者；分裂脑并不需要相等的纪元。如果历史已经分歧，隔离
写入者并为恢复保留两份历史，而不是假定
提升、降级或重放会合并它们。

## 跨机器的 Bot

当你在 **设置 → 连接** 中注册多个后端——本地运行时、远程网关、SSH 主机、Hermes Cloud 实例——花名册持久地显示来自**每个**已连接来源的 Bot：SSH 来源无需在远程机器上启动任何东西即被清点，而暂时不可达的机器保留其最后已知的行而不是消失。当同一个配置档名称存在于多个来源上时，句柄以 `@name-device` 消歧（例如 `@research-homelab`）。Bot 的聊天、会话、记忆和例程生活在拥有该配置档的机器上。

点击一个连接 Bot**不会**将你的窗口跳到那台机器上——留在你的聊天中并用 `@mention` 它，将其安排在群聊中，或用 **创建于** 选择器直接在其上创建新智能体。云和本地智能体以这种方式共享一个花名册：注册你的 Hermes Cloud 实例和你的桌面（例如，通过 Tailscale 或 SSH），它们的 Bot 可以互相发消息并坐在同一个房间中，每个智能体的工作在其自己的机器上运行。跨这些机器的 Bot 间 DM 自动经过 Desktop 中继（见上文*跨已连接机器的消息传递*）。

完整的多连接指南见[将 Desktop 连接到多个 Hermes 实例](./multi-connection-desktop.md)。

## 温热 Bot 后端（同时运行多少 bot）

每个本地 Bot 在其自己的后端进程中运行，Desktop 同时最多保持 **设置 → 高级 → 温热 Bot 后端** 那么多存活（默认 3，每个约 60 MB）。空闲后端在该设置旁边的空闲超时后被回收（默认 10 分钟）；跟随空闲回收消息之后的 `desktop.log` 中的 `Hermes backend for profile "<name>" exited (1)` 行就是那次清理，不是崩溃。你在每个槽都忙时打开的一个 Bot 最多等待 30 秒以获取槽位，然后以*等待空闲本地槽超时*失败。

读取另一个 Bot 的聊天历史和后台记录刷新**不**占槽位——只有交互式打开或运行中的回合才占。如果你驱动一个大型舰队（成员众多的群聊，或跨许多配置档的看板派发），将温热 Bot 后端提高到你觉得会同时活动的 Bot 数量，并给机器匹配的内存。将其设置得比实际使用的配置档更高只会增加启动工作。

## 将其关闭

Bot 模式是一个捆绑的桌面插件。在 **能力 → 插件 → Bots** 中将其 **Desktop** 开关关掉——花名册、例程窗格和编辑器中间件会实时注销，无需重启。你的配置档、会话和定时任务要么方式都不受影响；Bot 模式从不拥有你的数据，它只渲染它。

还有一个偏好设置可从常规侧边栏会话列表中隐藏规范 Bot 聊天，使它们只出现在 Bots 窗格中。（这使用核心隐藏会话标志；在较旧的网关上聊天只是保持可见。）
