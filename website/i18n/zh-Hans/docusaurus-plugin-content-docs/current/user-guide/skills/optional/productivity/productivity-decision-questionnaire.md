# 决策问卷

把用户无法独自回答的问题转化为一份**问卷**：一份 Markdown 文档，用户
可以交给某个人异步填写，或在一起开会时共同填写。接收者掌握用户所缺
的知识；问卷就把这些知识从他们那里引出来。

移植自 mattpocock/skills 以 MIT 许可发布的 `to-questionnaire` 技能。

## 何时使用

- 某个决策卡在只有他人才掌握的事实或判断上（领域专家、利益相关方、
  供应商联系人、运维）
- 用户说“我得就这件事问问 X”，或反复把某个决策推迟，等别人的意见
- 为一场会议做准备，会上必须拿到具体答复

当答案可以从环境中找到（代码库、文档、网络）时，不要使用本技能——
先自己去查。

## 核心原则：访谈的是“发送”，而非“主题”

用户无法回答关于主题本身的问题（这正是问题所在），但他们总会能够回答
关于“发送”的问题。只就这方面访谈他们，用两轮简短交流：

1. **要发给谁？** 角色、专长、与用户的关系。这决定了问卷的语气，以及
   它必须携带多少上下文。当你知道接收者是谁，以及他们掌握哪些用户不
   掌握的东西时，这一步就完成了。
2. **你需要拿回什么？** 用户无法独自解决的具体决策或事实。当你得到
   一份清晰的清单，列出用户必须能够据以行动或决策的内容时，这一步就
   完成了。

然后**撰写问卷**：按下面的结构起草问题，瞄准接收者所知与用户所需之间
的差距。将其写入当前目录下的 `decision-questionnaire-<slug>.md`（slug
取自主题），并报告绝对路径。当文件存在、且第 2 步中的每一项都被某个
问题覆盖时，这一步就完成了。

## 文档结构

把它框定为一份**发现问卷**：用户缺少上下文，接收者掌握上下文。问题按
最重要者优先排序（异步意味着你可能只有一次机会）。当问题数量超过
少数几个时，用 `##` 标题按主题分组。

模板：

```markdown
# <问卷标题>

**目的：** 这份问卷为何存在，以及它所承载的决策。

**来自：** <用户> · **致：** <接收者> ·
**你的回答将如何使用：** <它们将去向何处>

## 上下文

用一段话为没在用户脑袋里的接收者做好定位。足够他们好好回答，但别写成
一整页。

## 如何回答

截止时间与大致工作量。部分答案以及“我不知道”都有用：对任何不确定的
地方做标记，而非跳过。

## <主题标题>

### <一个问题 — 只含一个想法，绝不含多重>

_为何重要：<一行，仅在该问题可能被误读或引来敷衍回答时添加>._

>

## 还有别的吗？

收尾的兜底问题：有没有我们没问但我们应该知道的？
```

每个问题下方紧跟着放一条回答占位符（`>`）。

## 陷阱

1. **盘问用户关于主题的内容。** 他们答不上来——这正是文档存在的
   原因。只访谈“发送”。
2. **复合问题。** 每个问题只含一个想法；把带“和/或”的问题拆开。
3. **把关键问题埋没。** 最重要者优先；异步接收者会逐渐冷淡。
4. **上下文倾泻。** 一段用于定位的话，不是整部历史。
5. **在有歧义的问题上省略“为何重要”一行。** 正是这一行把敷衍回答
   变为有用的回答——但不要把它加到已经明确无歧义的问题上。
