# SDLC Review 技能

独立核实从一次 Kanban 实现运行移交给评审泳道的工作成果，然后予以批准、要求修改或上报。此技能评审的是交付物及其证据；它不会接管实现者的工作。

## 何时使用

当以下所有条件均成立时，使用此技能：

- 调度器已为你所领取自 `review` 泳道的任务创建了运行；
- 一位实现者提交了 `review_requested` 交接；
- 该任务在能够完成之前需要一份独立的裁决。

不要将其用于独立的下游评审卡片。下游卡片是普通实现工作，带有一份面向评审的规格说明，并通过自身的生命周期完成。

## 前置条件

- 一个 Kanban 工作上下文，包含当前任务与运行标识符。
- 原生 Kanban 工具：`kanban_show`、`kanban_comment`、`kanban_complete`、`kanban_request_changes` 以及 `kanban_block`。
- 当交付物为代码时，通过 `read_file`、`search_files` 和 `terminal` 访问工作区。
- 任务的原始规格说明、验收标准、交接摘要及先前运行历史必须能够通过 `kanban_show` 获取。

## 如何运行

此技能由评审调度器自动加载。在检查文件或选择裁决之前，先从 `kanban_show` 入手。

1. 阅读任务规格说明及最新的 `review_requested` 交接。
2. 检查实际交付物并运行相关核实。
3. 精确选择一种裁决：批准、要求修改或上报。
4. 在最终 Kanban 转换中记录具体证据。

## 快速参考

| 裁决 | 何时使用 | 最终操作 |
|---|---|---|
| 批准 | 验收标准与核实均通过 | `kanban_complete` |
| 要求修改 | 仍存在可纠正的实现缺陷 | `kanban_comment`，然后 `kanban_request_changes` |
| 上报 | 需要人工决策或外部前提条件 | `kanban_block` |

一次要求修改的转换会将任务返回其原实现者。当该实现者再次请求评审但未指定评审者时，持久化的评审者来源记录会将重新评审路由回同一评审者配置档。

## 评审视角

在每一轮中变换你审视工作的方式，而不是重复同样的检查。去相关的视角能捕捉不同的缺陷类别：对工件进行一次冷读，会浮现出实现者叙述会加以淡化归避掉的设计与正确性问题；实际操作运行，会暴露出无法复现的说法；严格的合约审计，会揭示隐秘的范围偏移。在第 3 轮重复第 1 轮的视角，大多只是重新发现第 1 轮已发现的内容。

从任务记录已提供的历史中确定当前轮次：数一下工作者上下文中「Prior attempts on this task」一节内的 `changes_requested` 条目数量（在 `kanban_show` 中也可见为先前的运行）。当前评审轮次为该数量加一。因此第 1 轮显示零次 `changes_requested` 尝试；第 2 轮显示一次；依此类推。

| 轮次 | 视角 | 如何应用 |
|---|---|---|
| 1 | 工件 | 在阅读实现者摘要之前，冷读 diff 或交付物。形成独立判断，然后将其与交接叙述进行比对，并调查每一处不一致。 |
| 2 | 执行 | 检出工作成果并通过 `terminal` 实际运行它：构建、测试，亲自操作运行所报告的行为。以实证方式核实每一项交接说法，而不是重读工件。 |
| 3+ | 合约 | 重读原始任务正文与验收标准，然后严格对照它们审计交付物。还要核实前几轮每一轮 `kanban_request_changes` 的每一项是否确实落地。 |

Procedure 一节中的基线职责在每一轮仍然适用；视角决定你优先并以最大权重进行的检查。

### 临时评审扇出时的视角变化

同样的原则也适用于 Kanban 评审泳道之外。当通过 `delegate_task` 派生出多个并行评审者时，给每一位评审者不同的视角——一份仅看 diff 的简报、一份全上下文简报、一份检出并运行的简报——而不是相同简报。相同的简报会产生相关联的裁决和重复的发现；不同的简报能在相同评审开销下覆盖更多缺陷类别。

## 流程

### 1. 从持久的任务记录中定位研究方向

调用 `kanban_show` 并确定：

- 原始任务正文与验收标准；
- 最新实现摘要及结构化元数据；
- 变更的文件、提交标识符及测试证据；
- 早期运行的评论与决定；
- 先前评审轮次的发现。

将交接视为待核实的说法，而不是工作正确的证明。

### 2. 将所请求的行为与交付的行为进行比对

将每项验收标准映射到具体的实现或输出证据。在决定是否运行更深入的检查之前，记录遗漏、语义变更及无关范围。

对于代码工作：

1. 使用 `read_file` 和 `search_files` 检查变更路径及其调用方。
2. 使用 `terminal` 检查 diff 并运行项目现有的focus测试、lint、类型检查或构建命令。
3. 在可行时操作运行所报告的失败路径及至少一条普通对照路径。
4. 检查与变更相关的错误处理、边界情况、并发边界、数据保全、安全边界及跨平台行为。
5. 确认测试断言的是行为，而不仅仅是快照化的源码文本或常量。

对于非代码工作：

1. 检查完整交付物，而不仅仅是其摘要。
2. 检查正确性、完整性、格式及来源。
3. 当引用的 URL 或外部事实影响裁决时，用适当的原生工具加以验证。

### 3. 选择一种裁决

#### 批准

只有在验收标准得到满足且证据充分时才批准。调用：

```text
kanban_complete(
    summary="Reviewed and approved. <what was verified>",
    metadata={"review_outcome": "approved", "reviewer_checks": [...]}
)
```

包含通过的精确检查，以及任何不阻碍验收的有限保留意见。

#### 要求修改

用于具体的、可纠正的缺陷。首先记录可操作的发现：

```text
kanban_comment(
    task_id="<current-task-id>",
    body="Changes requested:\n1. <file or artifact + defect>\n2. <required correction>",
)
```

然后将同一任务返回其实现者：

```text
kanban_request_changes(
    reason="<concise summary of the required corrections>"
)
```

说明缺陷在哪里、如何复现、为何违反任务，以及能解决问题的最小成果是什么。该转换不使用 blocker 复发计数。

#### 上报

只有在评审者与实现者无法在没有人工决策或外部前提条件的情况下解决问题时，才使用上报：

```text
kanban_block(
    reason="escalation: <decision or prerequisite required>"
)
```

解释被阻塞的决策以及继续所需的最小信息。

### 4. 保持角色分离

在担任评审者时不要编辑实现。要求修改，让实现者产出下一个候选版本；然后在下一轮评审运行中独立核实该候选版本。

## 陷阱

- **橡皮图章式批准：** 通过的交接摘要不是独立证据。
- **评审者自行实现：** 编辑交付物会隐藏归属并削弱重新评审的边界。
- **含糊的发现：** 「需要加工」不会给实现者一个可复现的纠正目标。
- **仅风格阻碍：** 当行为与仓库标准均已满足时，不要为偏好级别的琐碎问题要求修改。
- **跳过先前轮次：** 重新评审必须同时确认所要求的纠正以及先前通过行为的保持。
- **将 blocker 用于普通返工：** 可纠正的缺陷应归入 `kanban_request_changes`；将 `kanban_block` 保留给真正的外部阻塞或人工决策。
- **无证据即完成：** 每份批准摘要都必须指明实际检查的检查项或工件。

## 核实

在提交裁决前，确认：

- [ ] 已阅读 `kanban_show` 以获取当前任务与运行。
- [ ] 每项验收标准都已映射到证据。
- [ ] 已检查实际交付物。
- [ ] 已运行相关的focus检查，或在无法执行时记录了明确原因。
- [ ] 在重新评审中对先前要求的修改进行了重新测试。
- [ ] 已考虑无关的回归与范围变更。
- [ ] 裁决恰好使用一个最终操作。
- [ ] 摘要包含具体、非秘密的证据。
- [ ] 评审者未编辑任何实现文件。
