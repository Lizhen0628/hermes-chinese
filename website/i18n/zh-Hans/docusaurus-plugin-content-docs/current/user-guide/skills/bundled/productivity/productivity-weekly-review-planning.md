# 每周回顾与规划

在用户选定的系统上执行一次有边界的每周重置。这是一个具体的周期性任务，而非通用的生产力方法论——`weekly-review` 自动化蓝图会将其调度为定时任务。

## 何时使用

- “运行我的每周回顾。”
- “我承诺了什么，哪些在拖延？”
- “根据我的日历、任务和笔记规划下周。”
- “找出停滞的项目和等待中的事项。”
- 为计划中的每周回顾触发定时任务。

不适用场景：每日简报（参见 `google-workspace` 的 daily-brief 参考）或单一收件箱的整理（`email-inbox-triage`）。

## 流程

### 1. 设定系统与窗口

确认时区、回顾周期、规划范围、权威的任务/项目存储、日历、收件箱以及允许的写入操作。默认输出建议/草稿，而非直接修改。当来源冲突有明确的主数据源时即完成。

### 2. 回顾日历证据

加载 `google-workspace` 或相关日历连接器。检查已完成的一周中的会议和承诺，然后检查未来 1-2 周的截止日期、出行、准备和容量。记录过去事件隐含的后续事项以及未来的冲突。当回顾和展望两个维度都覆盖时即完成。

### 3. 清空收集收件箱

审查任务收件箱、笔记（`obsidian`、`notion`）、标记的邮件（线程级整理由 `email-inbox-triage` 负责）以及其他声明的收集点。将每一项转换为下一步行动、项目、等待、已安排、某天、参考、归档或删除建议。在范围获得批准之前不做修改。当归剩余的未处理项被计数并说明时即完成。

### 4. 核对进行中的项目

对于每个项目，识别期望成果、下一步行动、负责人、截止日期、阻碍项、最近有意义的活动和来源链接。标记无下一步行动、日期缺失、记录重复或状态矛盾的项目。当每个进行中的项目都可执行或被明确暂停时即完成。

### 5. 审查等待事项与承诺

找出用户做出的承诺以及他人尚欠的事项。提出带有日期和渠道的后续跟进建议。不要将沉默推断为完成。当每个等待事项都有负责人和下次回顾/跟进日期时即完成。

### 6. 构建考虑容量的计划

估算固定的日历负载，并选取一小批每周成果以及近期下一步行动。按后果、截止日期、依赖关系和投入程度排序；不要填满每个空闲小时。当计划符合实际容量并明确指出被推迟的工作时即完成。

### 7. 应用已批准的更新

仅在获得批准的情况下更新任务/项目、创建日历占用、归档已处理项并起草跟进事项。从服务商处读回每一条已更改的记录。当已验证的写入与回顾摘要相符时即完成。

## 输出结构

1. 成果与已完成的承诺
2. 逾期或有风险的事项
3. 等待/后续跟进
4. 停滞或状态不明项目
5. 下周成果与日历约束
6. 等待批准的更新建议
7. 覆盖缺口

## 陷阱

- 仅根据任务规划，而不考虑日历容量。
- 将所有未完成项都作为高优先级延续下去。
- 将无下一步行动的项目标记为进行中。
- 未经说明地删除或重新安排个人承诺。
- 将他人的沉默视为完成。

## 验证

- [ ] 已完成的一周和规划范围都已覆盖，或已说明缺口。
- [ ] 每个停滞/等待标记都能追溯到具体记录、事件或线程。
- [ ] 未获批准不修改任何任务、事件或笔记；已批准的写入已读回验证。
- [ ] 计划明确列出了被推迟的事项，而不仅是被选中的事项。
