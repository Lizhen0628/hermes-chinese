# Simplify Code — 并行审查与清理

用四个专注的审查者并行审查你近期的代码更改，汇总他们的发现，并
应用那些值得应用的修复。

**这是一次清理，而非缺陷排查。** 你是在提升已经能正常工作的代码的
质量——消除重复、摊平不必要的复杂度、削减浪费，并将权宜之计的
修复深化为真正的修复。不要在这里搜寻正确性缺陷；那是
`requesting-code-review` 的职责。

**核心原则：** 四个聚焦的审查者胜过一 个泛泛的审查者。每个审查者
针对单一类别的问题深入检索代码库——复用、质量、效率、高度——而不
会因覆盖全部四个方面而分散注意力。它们并发运行，所以你的等待时间
只相当于一次审查，而非四次。

## 何时使用

当用户说出以下任何一种话时，触发此技能：

- "simplify" / "simplify my changes" / "simplify these changes"
- "review my code" / "review my recent changes" / "clean up my changes"
- "/simplify"（如果他们保留了 Claude Code 的习惯）

用户可能附加的可选修饰语——尊重它们：

- **焦点：** "simplify focus on efficiency" → 仅运行效率审查者
  （或将汇总偏向该方面）。可识别的焦点：`reuse`、
  `quality`（也接受 `simplification`）、`efficiency`、`altitude`。
- **空跑：** "simplify but don't change anything" / "just report" → 运行
  四个审查者，呈现发现，不应用任何更改。应用前先询问。
- **范围：** "simplify the last commit" / "simplify staged" / "simplify
  src/foo.py" → 相应地缩小 diff 来源（见第 1 阶段）。

不要在每次编辑后自动运行此技能，也不要将其附加到无关
任务的末尾。它会消耗相当于四个子智能体的 token——仅在
用户明确要求时才调用。

## 流程

### 第 1 阶段 — 确定更改范围

捕获要审查的 diff。根据用户的请求选择来源，按以下
默认顺序：

```bash
# 1. Default: uncommitted working-tree changes (tracked files)
git diff

# 2. If that's empty, include staged changes
git diff HEAD

# 3. Scoped variants the user may request:
git diff --staged                 # "staged changes"
git diff HEAD~1                    # "the last commit"
git diff main...HEAD              # "this branch" / "my PR"
git diff -- src/foo.py            # specific file(s)
```

如果 `git diff` 和 `git diff HEAD` 都为空，且没有 git 仓库或没有
更改，则回退到用户明确指名的文件，或本次会话中最近创建/编辑的文件。
如果你确实找不到任何更改的代码，请说明并停止——没有什么可简化的。

捕获完整的 diff 文本。注意其大小：如果非常大（比如更改超过 2000
行），提醒用户四个子智能体各自携带完整 diff 将消耗大量 token，
并提出在继续之前缩小范围（按目录、按提交）。

### 阶段 2 — 并行启动四个审查者

使用 `delegate_task` 的**批处理模式**——将所有四个任务放在一个 `tasks` 数组中传入，使其并发运行。四路并发是此模式的恰当扇出数量；在任何默认安装中都在 `delegation.max_concurrent_children` 预算内。

**没有可用的委派？** 如果你在此上下文中无法调用 `delegate_task`（你是叶子子智能体、委派被禁用，或预算已耗尽），不要跳过审查或丢弃角度。在此上下文中，自己顺序地完成全部四个审查者角度的分析——采用相同的搜索标准、相同的发现格式。然后在最终总结中明确说明这是一次单遍内联审查，而非并行扇出，让用户知道实际运行了什么。

为**每个**审查者提供**完整 diff**（不是片段——跨文件的问题就隐藏在缝隙中），以及仓库绝对路径，以便他们能搜索更广泛的代码库。每个审查者获得 `terminal`、`file` 和 `search` 工具集（使他们能 `git`、`read_file` 及 `search_files`/grep）。

告诉每个审查者：
- 在现有代码库中搜索证据（不要仅凭 diff 推理）。
- **应用切斯特顿栅栏原则：** 在标记任何东西以供删除前，对该行运行 `git blame` 以理解其为何存在。如果你无法确定原始用途，将其标记为 `confidence: low`——不要猜测。
- 以结构化输出报告发现，附带具体代价、置信度和风险：
  ```
  file:line → 问题 → 代价（被重复/浪费/更难维护的是什么） → 建议修复 | confidence: high/medium/low | risk: SAFE/CAREFUL/RISKY
  ```
  **代价**字段迫使每条发现为自己辩护——一条无法阐明问题实际代价的发现很可能只是吹毛求疵。
  - **SAFE** = 已证不影响行为（未使用的导入、注释掉的代码、直通包装器）。自动应用这些。
  - **CAREFUL** = 改进而不改变语义（重命名局部变量、展平嵌套三元表达式、提取辅助函数）。应用时以测试验证。
  - **RISKY** = 可能改变行为或破坏公共契约（N+1 重构、公共 API 重命名、内存生命周期变更）。标记供人工审查——不要自动应用。
- 跳过吹毛求疵和纯风格改动。只标记能实质性改善代码的问题。

传递这四个目标（丢弃用户关注点排除的任何目标）：

**审查者 1 — 代码复用**
> 审查此 diff 中重复了代码库中已有功能的代码。搜索工具模块、共享辅助函数及相邻文件（使用 search_files / grep），查找新代码本可调用而非重新实现的现有函数、常量或模式。标记：重复现有函数的新函数；现有工具函数已经完成的手工逻辑（手动字符串/路径操作、自定义环境检查、临时类型守卫、重新实现的解析）。对每一个，指出应使用的现有事物及其所在位置。

**审查者 2 — 代码质量**
> 审查此 diff 中的质量问题。查找：冗余状态（重复现有状态或本可从中派生的值；本不应存在的缓存）；参数蔓延（本该重构函数的地方却硬塞进新参数）；带变体的复制粘贴（本应共享抽象的近重复块）；抽象泄漏（暴露内部、破坏现有封装边界）；字符串类型化代码（宜用常量/枚举/注册表的地方却用了原始字符串——标记前先检查规范注册表）；深层嵌套条件（三元链、3 层以上的 if/else 金字塔——用守卫子句、提前返回或查找表展平）；AI 生成的劣质模式（重复明显代码的多余注释，如在 `count++` 上方写 `// 增量计数器`；对已校验输入的不必要防御性空检查；绕过类型系统的 `as any` 强制转换；与文件其余部分不一致的模式）。对每一个，给出具体重构方案。

**审查者 3 — 效率**
> 审查此 diff 中的效率问题。查找：不必要的工作（冗余计算、重复的文件读取、重复的 API 调用、N+1 访问模式）；错过的并发机会（独立的操作顺序运行）；热路径臃肿（启动或每请求路径上的繁重/阻塞工作）；TOCTOU 反模式（操作前先检查存在性，而不是直接执行操作并处理错误）；内存问题（无界增长、缺少清理、监听器/句柄泄漏；作为闭包构建的长生命周期回调或对象捕获整个外围作用域——被捕获的一切在对象存活期间都保持存活，因此优先使用仅复制所需内容的小型类或显式字段结构体）；过宽的读取（切片即可时却加载整个文件）；静默失败（空的 catch 块、被忽略的错误返回、`except: pass`、无处理逻辑的 `.catch(() => {})`、错误传播缺口——这些会隐藏 bug，至少在吞掉前应记录日志）。对每一个，给出具体修复及为何更快或更安全。

**审查者 4 — 高度**
> 审查此 diff 中在错误深度上实现的变化——层叠在共享基础设施之上的权宜之计，而非对基础设施本身的修复。修复过浅的迹象：为处理单个调用者而在通用代码路径上添加的特例（`if (caller == X)` 分支、类型检查、魔法值逃生舱）；在调用点修补症状而同类调用点仍有同样缺陷；在早先的变通方案上再堆叠变通方案；为避免触及真正需改动之处而添加的包装器；为绕过损坏的默认值而引入的配置或标志，而非修复默认值。对每一个，识别该变化所规避的底层机制，并描述更深层的修复——泛化共享路径、修复根默认值，或修复整个 bug 类别——并诚实指出当更深层修复足够大时，它应作为自己的任务而非本次清理的一部分。先阅读周围代码和 `git blame`：看似权宜之计的东西有时是有意为之的边界（兼容垫片、分阶段迁移、vendored 代码隔离）。不要标记那些。

### 第 3 阶段 — 聚合与应用

等待四个审查者全部返回(批量模式下它们会一起返回)。

1. **合并**发现结果为一列表,在审查者意见重叠处去重——
   当两条发现针对同一行或同一底层机制时,将它们合并为一条。
2. **丢弃误报**——你拥有的上下文最多;你不必与审查者争论,直接静默丢弃薄弱或错误的建议即可。
3. **解决冲突。** 审查者之间可能有分歧(审查者 1:"使用现有的工具 X";审查者 3:
   "X 很慢,内联它")。默认的解决优先级:
   **正确性 > 用户明确表明的关注点 > 可读性/复用 > 微性能。**
   不要应用以牺牲清晰度为代价的性能"修复",除非该路径确实是热点。
   当两条建议互斥且都站得住脚时,选择改动代码更少的那条,并记下另一种方案。
4. **按风险等级顺序应用:**
   - **SAFE 优先**(自动应用):未使用的 import、被注释掉的代码、
     直通式包装器、冗余的类型断言。之后运行测试。
   - **CAREFUL 其次**(带验证地应用,一次一个文件):重命名局部变量、
     展平三元表达式、提取辅助函数、合并重复项。每处理完一个文件运行一次测试。有问题的就回滚。
   - **RISKY 最后**(标记待审查——**不要**自动应用):N+1 重构、
     公共 API 变更、并发修复、错误处理变更。逐条呈现,附上风险描述和测试覆盖情况。
     高度(Altitude)类发现通常归入此类——加深修复意味着触及共享基础设施,
     因此呈现更深层的修复方案,让用户决定是现在就做还是作为后续处理。
   如果用户选择了试运行(dry run),则呈现全部三个等级而不应用任何改动。
5. **验证**你没有破坏任何东西:对涉及的运行的项目的定向测试
   (而非全套件),并重新运行仓库所用的任何 linter/类型检查。若某个修复导致测试失败,回滚该单个修复并报告。
6. **总结**你改动了什么:按审查者类别和风险等级分组的已应用修复简要列表,
   外加你刻意跳过的任何发现及原因。如果你是内联运行(未委派),在此说明。

## 陷阱

- **不要展开超过 4 个审查者。** 更多审查者意味着更高成本和更多需要协调的
  冲突建议,而非更好的覆盖。四个类别已覆盖整个空间。
- **将完整 diff 交给每个审查者。** 把 diff 拆分给不同审查者
  有违设计初衷——跨文件重复和 N+1 只有在完整全貌下才会显现。
- **审查者是搜索,不是猜测。** 一条没有指向现有实用工具的复用类发现
  ("这里大概有个辅助函数")就是噪音。要求提供 `file:line` 证据;丢弃缺少证据的发现。
- **应用 ≠ 重写。** 这是对用户近期改动的清理,不是
  重构整个模块的许可。将编辑范围限定在 diff 所触及的内容,加上修复所需的
  最小周边改动。高度类发现是证明这条规则的例外:当正确的修复
  比 diff 更深层时,标记它——不要在一次性清理中单方面重建共享
  机制。
- **不要滑向 bug 猎取。** 如果审查者发现了真正的
  正确性缺陷,显著报告它——但作为单独的"发现 bug"备注,
  而不是掺入清理修复中。正确性审查是不同的
  环节,有不同的验证标准。
- **尊重项目约定。** 如果仓库有 AGENTS.md / CLAUDE.md /
  HERMES.md 或 linter 配置,把这些规则融入审查者提示词,让
  建议符合项目风格而非与之对抗。
- **过大的 diff 会撑爆上下文。** 如果 diff 巨大,先缩小范围再
  委派——四个子智能体各自背负 5000 行 diff 既昂贵又
  可能被截断。
- **过度信任死代码工具。** `knip`、`ts-prune` 和 `depcheck` 会标记
  被动态使用的导出(基于字符串的 import、反射)。移除前务必
  grep 该符号名——一份干净的工具报告并非证据。
- **未检查公共契约就重命名。** 导出名、API 路由
  路径、数据库列名和配置键都是契约——即便名字很差,
  重命名也会破坏消费者。将公共契约变更标记为 RISKY;绝不要
  自动重命名它们。
- **移除"不必要的"错误处理。** 空的 catch 块或被忽略的
  错误可能是有意为之——该错误在此上下文中是预期且无害的。标记它,不要移除;
  让人类决定。
- **并非每个特殊情况都是权宜之计。** 兼容垫片、分阶段迁移,
  以及围绕 vendored 代码的隔离层看起来像高度违规,但
  是刻意设计。在标记前检查 `git blame` 和周边注释;当意图不明时,标为
  `confidence: low`。
