# 合并协调器

以公正的第三方身份解决两个智能体分支之间的 git 合并冲突。当智能体针对同伴的工作解决冲突时，结果往往是覆盖同伴的改动或放弃自己的改动——它们缺乏同伴的上下文，且偏向自己的一方。本技能正是解决方案：一个中立的协调器，接收双方的 diff 以及双方声明的意图，产出合并结果，如同一个合并队列仲裁者。

## 何时使用

- 两个智能体分支/工作树在并行行动中发生碰撞（看板工程流水线、并行 PR 浪潮、多工作树重构）。
- 两个智能体的工作之间发生冲突导致 `git merge` 或 `git rebase` 中止，且任一原始智能体都不应自行裁决。
- 不要用于单个智能体自身工作内部的冲突，也不要用于琐碎的锁文件/生成文件冲突（那些应重新生成）。

## 先决条件

- 包含中止合并的仓库检出，或两个分支名称加上自行运行合并的权限。
- 双方的意图来源：看板完成摘要（`terminal` 运行 `hermes kanban show <task-id>`）、PR 描述，或至少每个分支的提交信息。
- 项目的构建/测试命令（如果有的话）。

## 如何运行

**独立运行** —— 由人类（或智能体）在冲突仓库内调用本技能：加载技能，然后自上而下遵循流程。

**派生中立智能体** —— 多智能体行动中的首选形态：

- `delegate_task`：派生一个子智能体，其任务消息中包含仓库路径、两个分支名称、双方意图摘要的原文，以及遵循本技能的指令。
- 看板原生方式：创建一个分配至**第三配置档**（不是任一工作者的配置档）的协调卡片，将两张冲突卡片链接为父节点 —— `kanban_create(title="reconcile branch-a x branch-b", assignee="reconciler", parents=["t_a", "t_b"])`。父节点链接会自动将双方的完成摘要带入协调器的上下文；卡片正文应指明仓库路径和两个分支。

## 快速参考

| Hunk 类别 | 定义 | 解决方案 |
|---|---|---|
| disjoint-intent（意图不相交） | 两项改动服务于不同目标，可以共存 | 合并两者 |
| same-question-different-answer（同一问题不同答案） | 双方对同一设计问题给出了不同答案 | 根据声明的意图选择其一；将决策显式呈现 |
| superseded（被取代） | 一方的前提在另一方改动后不再成立 | 保留存续的一方；注明原因 |

公正性契约：永远不要偏袒派生你的一方；只触碰冲突区域（不做顺手编辑）；每个设计问题的抉择都必须显式出现在交付摘要中。

## 流程

### 1. 收集双方信息

- 通过 `terminal` 运行：`git status`（确认冲突状态并列出冲突文件）、`git merge-base <A> <B>`，然后对每一方运行 `git log --oneline <base>..<side>` 和对每个冲突文件运行 `git diff <base>..<side> -- <file>`。在已中止的合并中，`HEAD` 是一方，`MERGE_HEAD` 是另一方。
- 收集各方意图：`hermes kanban show <task-id>` 获取完成摘要/元数据，或 PR 描述，或上述日志中的提交信息。在触碰任何文件之前，为每一方写下的一句话意图。
- 完成标准：你能用自己的话陈述双方意图，并拥有每个冲突文件的双方 diff。

### 2. 对每个冲突 Hunk 分类

- 用 `read_file` 打开每个冲突文件，定位每个 `<<<<<<<`/`=======`/`>>>>>>>` 块。
- 根据声明的意图（而非哪个改动看起来更好），为每个 hunk 从快速参考表中精确分配一个类别。
- 如果一个 hunk 包含多个独立决策（例如，一项能干净合并的新功能，再加上一个双方答案不同的样式/舍入选择），将其分解为子决策并逐一分类。
- 单个文件常常混合多种类别：一个 hunk 可能是设计冲突，而邻近的 hunk 可能是意图不相交的。按 hunk 分类，而不是按文件。
- 完成标准：每个 hunk 都有书面的类别和一句话理由。

### 3. 在公正性契约下解决

- 用 `patch`（或整文件重写时用 `write_file`）编辑每个 hunk：
  - disjoint-intent（意图不相交）→ 合并两项改动，使每个意图都得到完整满足。
  - same-question-different-answer（同一问题不同答案）→ 选择最能满足**已声明**意图的答案（例如，若任务要求正确性，则"严格验证"的意图胜过"快速默认值"）。永远不要折中成一个双方都未要求的混合方案。
  - superseded（被取代）→ 保留存续的一方；删除已失效的前提。
- 永远不要偏袒派生你的一方。如果意图确实相当，升级处理（阻塞看板卡片 / 回报）而不是猜测。
- 不要更改冲突标记之外的任何内容 —— 不做格式化、重命名或顺手修复。
- 通过 `terminal` 对每个已解决文件执行 `git add`。
- 完成标准：`search_files` 在仓库中找不到 `<<<<<<<` 标记，且每个已解决文件都已暂存。

### 4. 验证

- 通过 `terminal` 运行项目的构建/测试；至少导入/执行受影响的模块。两个意图都必须能在合并后的行为中观察到（例如，A 方的新语义和 B 方意图不相交的新增内容都同时存在）。
- 完成合并：`git commit`（默认合并信息加上列出 hunk 决策的正文即可）。
- 完成标准：验证通过且合并提交存在。

### 5. 交付

- 产出完成摘要，列出**每一个** hunk 决策：`file:lines — 类别 — 保留了哪一方 — 理由`。对于每个同一问题不同答案的 hunk，陈述设计问题及你选择的答案，以便人类可以否决 —— 永远不要埋没设计决策。
- 看板：`kanban_complete(summary=...)`。独立运行：打印摘要。
- 完成标准：摘要已交付且列出所有 hunk。

## 陷阱

- **偏袒自己**：如果你是由冲突智能体之一派生的，你在结构上就有偏差 —— 声明这一点，并有意识地权衡另一方的意图。优先采用第三配置档形态，以避免此问题发生。
- **折中**：在设计冲突上取折中会产生一个没人设计过的混合方案；选择一个答案并显式呈现它。
- **按文件分类**：文件通常混合多种 hunk 类别；将整个文件归为一类会静默丢弃意图不相交的改动。
- **顺手编辑**会使合并无法审查，并从原始智能体手中夺取决策权。
- **意图缺失**：仅凭提交信息可能单薄；优先使用看板完成摘要或 PR 描述。如果双方意图都无法还原，升级处理而不是猜测。
- **反复出现者**：跨轮次在**同一**文件上反复出现冲突是热点信号，不是常规协调工作 —— 标记它（例如一条 `hotspot: <path> — <reason>` 看板评论），以便编排器分解该文件，而不是针对其上的每一次新冲突进行串行协调。

## 验证

- `git status` 显示目标分支上是干净的树，且存在一个合并提交。
- 没有残留的冲突标记（`search_files` 模式 `<<<<<<<`）。
- 构建/测试通过；双方的意图均能明显体现，或被丢弃的一方已在摘要中显式命名。
- 交付摘要枚举每个 hunk 及其类别和理由。
