# Merge Reconciler

以公正第三方的身份解决两个 AGENT 分支之间的 git 合并冲突。智能体在面对同伴的工作时解决冲突，往往会可靠地覆盖同伴或放弃自己的更改——它们缺乏同伴的上下文，并偏向自己这一方。本技能正是解决之道：一个中立的协调器，接收双方的 diff 以及双方声明的意图，并产出合并结果，如同合并队列的仲裁者。

## 何时使用

- 两个智能体分支/工作树在并行战役中碰撞（kanban 工程流水线、并行 PR 浪潮、多工作树重构）。
- `git merge` 或 `git rebase` 在两个智能体的工作之间因冲突而中止，且原智能体都不应自行裁决。
- 不要用于单个智能体自身工作内部的冲突，也不要用于琐碎的锁文件/生成文件冲突（应改为重新生成它们）。

## 前提条件

- 一个包含已中止合并的仓库检出，或者两个分支名加上自行运行合并的权限。
- 双方的意图来源：kanban 完成摘要（`terminal` 运行 `hermes kanban show <task-id>`）、PR 正文，或者至少每个分支的提交信息。
- 项目的构建/测试命令（如果存在的话）。

## 如何运行

**独立运行**——人类（或智能体）在有冲突的仓库内调用此技能：加载技能，然后自上而下遵循流程。

**派生的中立智能体**——多智能体战役中的首选形态：

- `delegate_task`：派生一个子智能体，其任务消息包含仓库路径、两个分支名、双方意图摘要（逐字），以及遵循此技能的指令。
- Kanban 原生：创建一个协调卡片，分配给**第三个配置档**（而非任一工作者的配置档），并将两个冲突卡片都链接为父级——`kanban_create(title="reconcile branch-a x branch-b", assignee="reconciler", parents=["t_a", "t_b"])`。父级链接会自动将双方的完成摘要带入协调器的上下文；卡片正文应写明仓库路径和两个分支。

## 快速参考

| 差异化块类别 | 定义 | 解决方式 |
|---|---|---|
| disjoint-intent（意图不相交） | 两个更改服务于不同目标，可以共存 | 合并两者 |
| same-question-different-answer（同一问题不同答案） | 双方对同一个设计问题给出了不同回答 | 依据声明的意图选**一个**；表面化该决策 |
| superseded（被取代） | 一方的前提在另一方的更改后不再成立 | 保留存续的一方；说明原因 |

公正性契约：绝不偏袒派生你的一方；只改动冲突区域（不做顺手编辑）；每个设计问题的选择都必须明确出现在交接摘要中。

## 流程

### 1. 收集双方

- 通过 `terminal` 运行：`git status`（确认冲突状态并列出冲突文件）、`git merge-base <A> <B>`，然后对每一方运行 `git log --oneline <base>..<side>`，并对每个冲突文件运行 `git diff <base>..<side> -- <file>`。在已中止的合并中，`HEAD` 是一方，`MERGE_HEAD` 是另一方。
- 收集每一方的意图：`hermes kanban show <task-id>` 获取完成摘要/元数据，或 PR 正文，或上述日志中的提交信息。在触碰任何文件之前，为每一方写下意图的一句话。
- 完成标志：你能用自己的话陈述双方的意图，并拥有每个冲突文件的双方 diff。

### 2. 对每个冲突差异化块分类

- 用 `read_file` 打开每个冲突文件，定位每个 `<<<<<<<`/`=======`/`>>>>>>>` 块。
- 根据声明的意图——而非哪个更改更好看——为每个差异化块恰好分配快速参考表中的一个类别。
- 如果单个差异化块包含多个独立决策（例如，能干净合并的新逻辑，加上双方给出不同回答的样式/舍入选择），将其分解为子决策并分别分类。
- 单个文件常常混合类别：一个差异化块可能是设计碰撞，而邻近的差异化块是意图不相交的。按差异化块分类，而非按文件分类。
- 完成标志：每个差异化块都有书面的类别和一行理由。

### 3. 在公正性契约下解决

- 用 `patch`（或整文件重写用 `write_file`）编辑每个差异化块：
  - disjoint-intent → 合并两个更改，使每个意图都得到完全满足。
  - same-question-different-answer → 选择最服务于**声明的**意图的答案（例如，如果任务要求正确性，"严格验证"的意图胜过"快速默认值"）。绝不要折中成一个双方都未要求的混合体。
  - superseded → 保留存续的一方；删除已死的前提。
- 绝不偏袒派生你的一方。如果意图确实并列，应升级处理（阻塞 kanban 卡片/回报），而非猜测。
- 冲突标记之外的任何内容都不得改动——不做格式化、重命名或顺手修复。
- 通过 `terminal` 对每个已解决的文件执行 `git add`。
- 完成标志：`search_files` 在仓库中找不到 `<<<<<<<` 标记，且每个已解决文件都已暂存。

### 4. 验证

- 通过 `terminal` 运行项目的构建/测试；至少导入/执行被触动的模块。双方的意图都必须在合并后的行为中可被观察到（例如，A 方的新语义和 B 方的意图不相交的新增都必须存在）。
- 完成合并：`git commit`（默认合并信息加上列出差异化块决策的正文即可）。
- 完成标志：验证通过，且合并提交存在。

### 5. 交接

- 产出一份完成摘要，列出**每个**差异化块决策：
  `file:lines — class — which side(s) kept — rationale`。对于每个 same-question-different-answer 差异化块，陈述设计问题及你所选择的答案，以便人类可以否决它——绝不埋没任何设计决策。
- Kanban：`kanban_complete(summary=...)`。独立运行：打印摘要。
- 完成标志：摘要已交付并列出所有差异化块。

## 陷阱

- **自我偏袒**：如果你是冲突智能体之一派生的，你就结构性地有偏见——应声明这一点，并有意识地权衡另一方的意图。优先采用第三配置档形态，以便此问题永远不会出现。
- **折中之举**：在设计碰撞上折中会产生无人设计的混合体；选择一个答案并将其表面化。
- **按文件分类**：文件通常混合差异化块类别；将整个文件归为一个类别会静默丢弃一个不相交的更改。
- **顺手编辑**：会让合并无法审查，并从原智能体那里夺走决策。
- **缺失意图**：仅凭提交信息可能太单薄；优先采用 kanban 完成摘要或 PR 正文。如果双方的意图都不可恢复，应升级处理而非猜测。
- **惯犯**：跨轮次在**同一**文件上重复冲突是热点信号，而非例行的协调工作——应标记它（例如 `hotspot: <path> — <reason>` 的 kanban 评论），以便编排器分解该文件，而不是串行地协调它上面每一次新的碰撞。

## 验证

- `git status` 显示目标分支上干净的工作树，并带有合并提交。
- 不再残留冲突标记（`search_files` 模式 `<<<<<<<`）。
- 构建/测试通过；双方的意图都被明确证明存在，或被丢弃的一方在摘要中被明确点名。
- 交接摘要列举每个差异化块的类别和理由。
